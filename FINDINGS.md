# Findings

Non-obvious facts the code and tests do not record: upstream CHIRP defects we route around,
external API, browser and platform behaviour, measurements, and the reasons behind decisions.
Each entry starts with a **bold slug** (grep target; some are cited from code) and its discovery
date. If a comment, test or CLAUDE.md already states it, it does not belong here.

The CHIRP pin is `d99bb227` (2026-11-13). Corpus counts were measured at `29592824` or earlier
and drift on each bump.

## CHIRP / Pyodide runtime

- **async-pyproxy-calls-behave-like-runPythonAsync** (2026-09-24): `pyodide.ffi.run_sync` inside a coroutine called through a `PyProxy` works exactly as under `runPythonAsync`, so `callPromising` is not needed. `pyodide.isPyProxy` does not exist in 0.27, which is why `rpc-dispatch.ts` duck-types on `destroy`.
- **no-jspi-browsers-lose-only-the-clone-path** (2026-09-24): also lacking JSPI: Firefox ESR. Reproduce on Firefox by setting `javascript.options.wasm_js_promise_integration` to false. Firefox 152+ has both JSPI and native `navigator.serial`.
- **f4hwn-release-archive-is-bundled-lazily** (2026-09-22): v4.3.0 to v4.3.2 shipped identical driver bytes; v4.3.2 is the one bundled. The drivers declare neither `_memsize` nor `match_model`, so WebCHIRP cannot build an offline image or detect a metadata-less image for them. Nobody has tested real-radio clones with them.
- **f4hwn-image-selection-is-required** (2026-09-23): the releases share one vendor/model/class identity, so image metadata cannot identify the release, and a successful load does not prove the user picked the right one.
- **f4hwn-older-driver-drops-new-key-actions** (2026-10-16): the v6.1.0 driver's `get_action` clamps any key action index past its list to 0, so it reads v6.2.0's appended "TONE CALL" as NONE, and a write after any settings edit stores NONE (`tests/channels/f4hwn-releases.mjs`). Even a two-line driver diff can lose radio state under the previous release, so each release is bundled as its own module.
- **f4hwn-firmware-release-without-driver-change** (2026-10-29): v6.3.0's driver differs from v6.2.0's only in `DRIVER_VERSION`, which the driver only shows as a read-only settings label; the release's firmware changes (overlay API v3, new Labs apps) leave the memory and settings layout alone. A firmware bump is not evidence of a layout change, so diff each release's driver against the last before assuming one.
- **uv5r-reports-a-finished-override-upload-as-an-error** (2026-10-16, CHIRP `7a4123ad`): the Range Override Parameter is armed by typing `UseAtOwnRisk`, but `set_range_flag` holds that value as a list of character codes, so a grep of the driver for it finds nothing. Desktop CHIRP shows the post-upload `RadioError` as an error dialog too, titled "Error communicating with radio": `CloneThread.run` (`chirp/wxui/clone.py`) hands every exception from `sync_out` to `show_error`. Raising is the only way a driver can show a message after an upload: `RadioPrompts` has `pre_download` and `pre_upload` but nothing for afterwards. Neither the commit (`5a74af53`) nor kk7ds/chirp#380 says why CHIRP must be restarted. Sentry WEBCHIRP-FRONTEND-22 holds one (a Radioddity UV-5RX3 on Windows, 2026-10-14); an origin rule could not have told it apart, because `_do_upload` raises its real failures from the same frame.
- **uv5r-upload-issue-mixes-two-failures** (2026-10-16): the other two events in WEBCHIRP-FRONTEND-22 are a genuine refusal, not the override report: "Image not supported by radio" from `uv5r.py:622`. That check compares byte 3 of the radio's ident with byte 3 of the image, and refuses when exactly one of them is a 220 MHz (tri-band) radio. The override does not bypass it. Both events came from one macOS user with `BaofengUV5RGeneric` (2026-10-13). In each of two page loads they imported an image file, not a download from the radio, and every upload failed: two in the first load (only the second reached this issue), one in the second after a reload. They never succeeded. All three events share one group because `runtimeFingerprint` groups by the raising Python function, and the issue's title is the latest event's message (**runtime-errors-grouped-as-one-per-class**). So the issue read as three "NOT an error" events, and the triage that joined trace IDs to `flow.completed` counted all three as recovered. Read each event's own message before generalising from an issue title.
- **upstream-tests-skip-power** (2026-07-29): CHIRP has no byte-level image round-trip test, and the shared `assertEqualMem` (`chirp/tests/base.py`) skips `power` (`# FIXME`) for `test_get_set_all`, `test_copy_all` and `test_edges` alike, so power round-trip bugs go unnoticed upstream; `ftm7250d.FTM7250Radio`'s Hi/Low swap, which shows only on an edited row, is pinned in `tests/channels/channel-round-trip.mjs`. `chirp/tests/driver_xfails.yaml` lists only brute-force xfails, so every image in `chirp/tests/images/` should detect and load cleanly.
- **idrp-never-registers** (2026-07-30): `idrp.IDRPx000V` has no `@directory.register` upstream, so it is missing from the catalog even in desktop CHIRP; the pyserial shim makes it import, not register.
- **blank-instances-misreport-state** (2026-03-14): `radio_cls(None)` is not a smaller parsed instance: `get_settings()` can throw on it, and `get_features()` can differ (power levels, `valid_bands` of `(0, 0)`). Derive anything feature-based from the session's image, never from a blank instance.
- **upstream-get-max-defect** (2026-03-14): `RadioSettingValueFloat.get_max()` has no `return` (`chirp/chirp/settings.py`), which is why float bounds fall back to `_max`.
- **ft1d-smartbeacon-low-speed-bound** (2026-10-17, CHIRP `7a4123ad`): the late-binding SmartBeacon `get_max` lambda (`ft1d.py:1778`, `vx8.py:1623`) is pinned by `tests/channels/smartbeacon-low-speed-bound.mjs` and worked around in `workarounds/ft1d.py` and `workarounds/vx8.py`. Beyond those: VX-8R has no SmartBeacon menu; the high-speed maximum is 70 on FT1D and 90 on ft2d; every zeroed map made a from-scratch binary export of an FT1D-family radio fail (WEBCHIRP-FRONTEND-2G, an FT5D). Desktop CHIRP reads `get_max()` unguarded too (`wxui/common.py:750`; not run). Not yet reported upstream.
- **parse-freq-negative-defect** (2026-07-30): upstream `chirp_common.parse_freq()` always adds the fractional part: `"-0.600000"` → +600000, `"-5.600000"` → −4400000 (pinned in `tests/channels/row-normalization.mjs`). CHIRP's own CSV driver parses with it, so an imported signed Offset is wrong before the app sees it: `-5.600000` arrives as `-4.600000` (`format_freq` mishandles the sign too) and cannot be recovered, and `-0.600000` arrives unsigned with no trace. Before #338 the first was written as `+` 3.4 MHz (#337).
- **the-first-yield-moves-python-off-the-jspi-stack** (2026-09-26): in Chrome the per-import yield makes the 194-module sweep ~7× faster (~1.0 s vs ~6.9 s). One yield before the loop is enough and the yields cost nothing. Node shows no difference, so no test can catch a regression. Hypothesis: a dispatched call runs on a JSPI suspendable stack where every Wasm-to-JS call (each FS syscall) pays a stack switch, and the first `await` moves the rest onto the ordinary stack. Rule: a long synchronous stretch dispatched from JS yields once before it starts.
- **all-driver-import-mechanics** (2026-07-30): at the current pin every module imports, but keep the per-module skip reporting: grepping for `import serial` cannot judge importability (`hf90`/`tmv71_ll` import it inside functions).
- **transport-disconnect-events-name-different-things** (2026-08-24): a radio switched off behind a cable that stays connected fires no disconnect event on any transport; it shows up only as a clone timeout.
- **shim-owes-pyserial-return-values-not-just-methods** (2026-09-05): drivers consume `WebSerialPipe` return values, not just method names (issue #79). When auditing the shim, grep drivers for code that *uses* a return value, not for the method names.
- **drivers-reach-the-pipe-through-chirp-platform** (2026-10-10, CHIRP `82c6f4c3`): a driver can read pipe attributes indirectly through `chirp/platform.py`, which a grep of `chirp/drivers` for `pipe.` misses (`UV5RMini`'s `is_ble_serial(self.pipe)`, pinned in `tests/channels/clone-ble-detection.mjs`). Image loads never call `sync_in`, so only a clone test catches such a dependency.
- **framing-is-set-after-open-but-never-mid-clone** (2026-09-05, CHIRP `80d93fe5`): every `parity`/`stopbits`/`bytesize` assignment comes after the port opened but before the operation's first byte (`tg_uv2p`/`tk8180` two stop bits; `tk280`/`ft2800`/`tk760g`/`tk8102`/`hg_uv98` even parity; `ft450d` all four). Deliberately ignored: `xonxoff` (no driver assigns it), `rtscts` (only ever `False`), `tk3140`'s `pipe.databits` typo (dead on real pyserial too). Expect probe loops that reopen up to six times (`thd72`/`thd74`/`tmv71`, `ts480`/`ts590`, `tmd710`). `icf.start_hispeed_clone` switches to 38400 mid-clone for 11 Icom modules with `_can_hispeed = True`. `tmd710` formats `pipe.baudrate` with `%i`, so the pipe must be seeded from `BAUD_RATE`.
- **mixed-mutability-settings** (2026-10-10, CHIRP `7a4123ad`): desktop CHIRP contradicts itself on a multi-value `RadioSetting` where only some values are immutable. Its editor enables each value on its own (`wxui/common.py:659`), but `_remove_dead_settings` (`wxui/settingsedit.py:186-200`) drops the whole setting when any value is immutable, so an edit to the mutable sibling is silently lost. No image in `chirp/tests/images/` (363 scanned) has such a setting, so no driver's `set_settings` has been seen receiving one.
- **drivers-refuse-their-own-settings** (2026-10-14, CHIRP `7a4123ad`): a driver's `set_settings()` can refuse the tree its own `get_settings()` built, because range checks live in apply callbacks rather than in the `RadioSettingValue`. That breaks the round trip upstream's own `test_same_settings` (`chirp/tests/test_settings.py`) requires, so it is an upstream defect; upstream CI passes only because no test image holds the value. The `kguv9dplus` cases are pinned in `tests/channels/kguv9dplus-empty-frequency.mjs` and `tests/settings/driver-refused-settings.mjs`; its immutable caller ID codes and `stun.scc`, and its receive and transmit limits (`RadioSettingValueString(1, ...)`, so an empty one never initializes), are pruned by the runtime before the write. One user's KG-UV9GX tripped this on every export (WEBCHIRP-FRONTEND-2D, six attempts) and on an upload (-2E); Sentry scrubs the numbers, so which field held the 0 is unknown, and the planted zeros are a reproduction. Desktop CHIRP meets this only after an edit, because only its editor's change handler calls `set_settings()`. Since 2026-10-16 `IGNORED_CHIRP_ERRORS` in `web/js/sentry.ts` drops both of CHIRP's `InvalidValueError` classes, so these refusals stopped reaching Sentry before #267 (2026-10-19) fixed them.
- **runtime-errors-cross-as-an-envelope** (2026-09-29): V8 formats `Error.stack` at construction, before a subclass sets `name`, so a `RuntimeCallError`'s stack still begins `Error: ...`; build its detail from the envelope, not from `stack`. `harness.runPython()` snippets bypass the dispatcher and reject with Pyodide's `PythonError` text; a test that wants the typed error calls `harness.rpc()`.
- **undecodable-memories-couple-download-to-erase** (2026-09-06): upstream renders an undecodable memory as an error row; we return `unreadableChannels` instead, because a placeholder row could be mistaken for a writable one.
- **undeletable-channels-raise-on-setattr** (2026-10-17, CHIRP `7a4123ad`): 19 driver modules list `empty` in `Memory.immutable` for slots that always exist (fixed GMRS/FRS/MURS or call channels, e.g. `radioddity_gm30` 1-54; Sentry WEBCHIRP-FRONTEND-2N). The four driver overrides of `check_set_memory_immutable_policy` (`btech`, `uv5r`, `gmrsv2`, `retevis_rb17p`) only relax it, so the `RuntimeUnsupportedError` it was meant to produce for an omitted slot never ran for any driver. Desktop CHIRP refuses delete and cut on such a slot ("Memory %i is not deletable", `wxui/memedit.py`): its delete erases the selection in order and stops at the first such slot (`_delete_memories_at`), while its cut refuses the whole selection up front. `Memory.dupe()` is shallow, so a copy shares `immutable` with its source.

## Channel grid / CSV

- **csv-radio-is-not-a-round-trip-surface** (2026-07-30): `generic_csv.CSVRadio` is CHIRP's import/export vehicle, not a lossless staging format; a header-only CSV raises `InvalidDataError("No channels found")`, so never route the empty-grid schema through it.
- **power-labels-beat-watts-in-rows** (2026-07-30): rows carry power as the driver's label because 8 driver classes collapse distinct levels onto one watt string after 1-dp rounding (e.g. `retevis_rt21.RT619Radio`), and CHIRP itself shows labels except for `has_variable_power` radios. Radio writes are unaffected by band-keyed level lists: those drivers re-resolve power from frequency.
- **grid-width-comes-from-its-editors** (2026-09-08): never give one grid column `width: 100%`: it squeezes the others instead of letting the grid scroll.
- **grid-runaway-scroll-was-not-android** (2026-10-13): issue #262 (the grid scrolling by itself, reported from Android Chrome) reproduced in desktop Chromium too; `tests/e2e/app.mjs` pins it. A hidden Claude browser pane throttles `requestAnimationFrame` to seconds or stops it outright, so the grid stops re-windowing there; measure windowing in Playwright.
- **cell-rules-live-in-python-only** (2026-10-09): measured in Chrome on the dev server, a committed cell's round trip is ~6 ms median (max ~14 ms over 20) once warm and ~67 ms for the first commit after selecting a UV-5R-family radio (radio built from zeroes) -- the only case over the 50 ms budget. Some driver messages map to no column (`Tx freq … out of supported range`): they reach Debug Output but highlight no cell. `normalize_rows` stays separate: it renders CSV export text through `import_logic`, a different job.
- **id800-refuses-a-plain-dv-memory** (2026-11-17, CHIRP `d99bb227`): pinned by `tests/channels/dstar-round-trip.mjs` (the preflight passes, the export refuses). Desktop CHIRP's grid sends the same plain Memory and should fail the same way (not run).

## Radio images (.img) & metadata

- **wrong-match-is-worse-than-no-match** (2026-07-23): since CHIRP 29592824 (2026-09-29) `CloneModeRadio.match_model()` returns False by default, so the all-drivers sweep only detects a metadata-less image through a driver that implements `match_model()` itself (118 driver files do, e.g. uv5r, h777, many Icom ic*/id*, and external formats such as tk8160 .dat, thd72 .mc4, ft1d/ft70 ADMS). That is upstream's intent, not our bug.
- **export-ran-no-preflight** (2026-10-15): issue #266 (Wouxun KG-XS20G Plus): an export that ran no preflight turned a refused AM cell, copied from another radio's channels, into a BINARY EXPORT ERROR, a Sentry capture and the title of the user's bug report; it now runs the upload preflight (`tests/channels/unsupported-mode.mjs`). Unlike Power, Mode has no closest value to move to: desktop CHIRP's import refuses such a memory too (`import_logic.import_mem` → `validate_memory` → `DestNotCompatible`), so the cell stays for the user to change or delete. `kg935g`'s KG-XS20G family stores only a wide/narrow bit (`iswide`); the KG-1000G Plus (`kguv980p`) offers AM and NAM.
- **image-corpus-measurements-need-fresh-runtimes** (2026-07-30): driver imports accumulate in one Pyodide session, so walking `chirp/tests/images/` in one runtime does not measure each image's own load path: measure per image, or import every driver once and assert the matcher resolves either CHIRP's own detection or nothing. Corpus counts (2026-09-14: 361 images, 108 without a trailer, the 253 with one all agreeing with detection) predate CHIRP 29592824; re-measure after every submodule bump.

## Radio specs (radio-specs.json)

- **radio-specs-are-researched-not-generated** (2026-09-24): research rules for `radio-specs.json`. **Driver bands are not radio bands**: Chinese HT drivers accept wide ranges whatever the market version. **"Dual watch" is not dual receive**: only true second-receiver radios (Kenwood TH-D7x/TM-V71, Icom IC-W32/ID-51, Wouxun KG-UV8D/9D, Yaesu FT-8x00) are `true`. **Maker figures are often inflated**, so when sources conflict, leave the field null. Leave `min` power null when only a maximum is published. Do not cut a continuous range at conventional band edges, and check manuals for receive gaps (US cellular 824–894 MHz, Yaesu 729–800 MHz) that rigpix flattens. `1.25 m` means only 219–225 MHz or a set sold as a 220 rig; 200–260 MHz on unlocked Chinese HTs is `Other`.

## Repeater directories

- **rsgb-etcc-api-shape** (2026-07-31): `https://api-beta.rsgb.online` documents itself as HTML at `/`. Endpoints are `/<name>/<arg>`, and the arg is mandatory: leave it out and you get the HTML index. `/band/`, `/locator/`, `/callsign/`, `/keeper/` and `/all/<anything>` return `{"data":[…]}`. `/aprs/<call>` returns `{"callsign","passcode"}` without the wrapper.
- **rsgb-locator-lookup-is-not-a-prefix-search** (2026-07-31): about 26% of records carry only a 4-character locator, so an exact 6-character `/locator/` query misses about a quarter of the directory.
- **rsgb-record-semantics** (2026-07-31): `type` is an undocumented code. Use `tx == rx` to spot simplex stations instead. `dbwErp` is in dBW.
- **rsgb-has-no-lat-lon** (2026-07-31): `extraDetails.ngr` is an OS grid reference on OSGB36, so comparing it with a WGS84 fix needs a datum shift. Over the UK, a 6-character box is about 4.6 km N-S by 4.5–6 km E-W (not the equatorial 9.3 km). A 4-character centre can be about 70 km from the station.
- **coep-blocks-plain-cross-origin-images** (2026-08-17): under the dev server's COEP, a plain cross-origin `<img>` is blocked silently (`ERR_BLOCKED_BY_RESPONSE.NotSameOriginAfterDefaultedToSameOriginByCoep`). Pages sends no COEP, so the failure only shows locally. A new cross-origin asset needs a CORS-mode load against an upstream that sends ACAO, or an upstream that sends `Cross-Origin-Resource-Policy: cross-origin`.
- **irts-api-mostly-matches-the-shared-rxf-contract** (2026-08-27): IRTS is api.webchirp.org's own route, not a proxy. It speaks the same RXF contract as the proxied directories and covers `ie` and `gb` (Northern Ireland included).
- **only-the-range-bounds-an-rxf-query** (2026-09-19): measured on RepeaterBook: an unfiltered query returned the whole directory (18.4 MB), `country=us` 10.1 MB and lat/lon/`range=30` returned 68 KB. Adding `country` to a position changed nothing, so only the range bounds the answer. A country-only query (even for the US) is still allowed on purpose, so small countries can be imported whole.
- **repeater-record-modes** (2026-10-09): `REPEATER_MODES` is closed over the spellings the four sources were seen sending live. No source reports AM, so AM is left out. Recheck the live spellings before adding a mode.
- **one-repeater-row-builder** (2026-10-09): besides the fixture snapshot, parity with the retired builders was checked once, locally, against live answers. The data was przemienniki.net `country=pl` (646 entries), RepeaterBook within 80 km of New York, IRTS `ie` and `gb`, and RSGB IO82/IO83/IO91/IO93. It held except for the three known differences.
- **a-position-reaches-three-parties-at-three-precisions** (2026-10-15): what the privacy policy's location section rests on. Only `api.webchirp.org` gets the exact pair, as `latitude`/`longitude` query parameters (directory queries) or `lat`/`lon` (the `/cities` proximity hint). The RSGB never gets coordinates: `squaresForRadius` turns the position into 4-character locator squares, each 1° by 2°, and only those go into the `/locator/` URLs. The OSM tile server gets `{z}/{x}/{y}` tile indices around the position, never coordinates. The locate button is not the only way a position leaves the device: typing coordinates or a locator, picking a place or dragging the map send it too. The repeater form keeps the position in memory only, never in storage.

## WebUSB serial adapters

- **ffe0-radio-uart-needs-acknowledged-writes** (2026-11-09): a Baofeng UV-5R Mini with "Wireless CPS" on advertises the name "walkie-talkie" and exposes three GATT services: FFE0 (FFE1: write, write-without-response, notify; FF31: write only), AE30 and AE3A (the vendor app's; not used). The clone protocol runs over FFE1 alone at no settable rate. In an independent Web Bluetooth programmer (esetgo.com), unacknowledged 20-byte writes were intermittently dropped under clone-sized bursts and corrupted uploads; writing each chunk with a response fixed it, which is why ffe0-uart.ts prefers responses. Whether the radio advertises FFE0, so that the service filter alone finds it, was not established; the chooser also lists the name. CHIRP's `UV5RMini` switches to its BLE upload block size (0x80) when the pipe reports a Bluetooth port, which `WebSerialPipe.port` does for this transport. Tested on a real UV-5R Mini from Chrome on macOS (2026-11-09): download, .img export, an edited upload, and restoring the exported .img all succeeded with no workaround.
- **ch340-version-not-bcddevice** (2026-07-28): branch CH340/CH341 behaviour on the chip version (vendor request `0x5F`), never on USB `bcdDevice`: a 0x1a86:0x7523 cable reporting `bcdDevice 0xc233` still reports version 0x30/0x31.
- **loopback-cannot-verify-baud** (2026-08-15): to check a divisor on hardware, cross-wire a second adapter running at a known rate; a TX-to-RX jumper on one adapter cannot catch a wrong rate.
- **one-bulk-in-transfer-at-a-time-drops-bytes** (2026-08-17): FT232R measurement, the one not in the driver comments: with one transfer outstanding, 2 of 30 runs lost bytes (Pixel 10, Chrome 151, 115200). Failure rates are low, down to about 7% per run, so a clean run proves nothing: the fix rests on reproducing the loss plus the structural argument. A bare pump benchmark catches the loss less often than the full loopback suite.
- **driving-the-loopback-page-on-a-phone** (2026-08-17): chip defects show up on phones, which no CI covers. Rig: wireless adb (`adb pair <host>:<pairingPort> <code>`, then `adb connect <host>:<connectPort>`; the two ports differ, both come from `adb mdns services`, and pairing is advertised only while the dialog is open). `adb reverse tcp:8000 tcp:8000` serves `npm run dev`; `http://localhost:8000` is a secure context on Android, so WebUSB works without HTTPS. `adb forward tcp:9222 localabstract:chrome_devtools_remote`, then CDP: `Target.createTarget` (Chrome for Android has no `/json/new`), `Runtime.evaluate` with `userGesture: true` for `requestDevice()`, then `import()` the driver and loop `runLoopbackSuite`. One run takes about 21 s.
- **cp210x-holds-flow-control-in-a-block-nothing-resets** (2026-08-19): `IFC_ENABLE` disable/enable does not reset the `SET_FLOW` block, so handshaking and XON/XOFF left by a previous host driver persist into our session unless the block is rewritten.
- **baud-rate-is-latched-at-open** (2026-09-05): Web Serial has no in-place re-rate, and `getInfo()` does not report the rate. The only way is `close()` + `open()` on the same `SerialPort`, which needs no user gesture or chooser because permission belongs to the port object.
- **webusb-chip-framing-is-unit-tested-not-measured** (2026-10-10): the four chip drivers' framing encodings (as the Linux drivers do them) are pinned per control transfer by the tests, but none has been measured on an adapter; a TX-to-RX jumper cannot catch a wrong frame either, because both ends share it (**loopback-cannot-verify-baud**).
- **webusb-input-lines-are-polled** (2026-10-10): PL2303 has no kernel poll for its input lines (the kernel only caches the interrupt endpoint's UART-state notifications), so `getSignals()` reads the active-low register usb-serial-for-android uses (`0x87`, or `0x80` on HXN). It has not been measured on an adapter: if the control-line case fails on a jumpered PL2303, suspect that register first.
- **cdc-polyfill-1.0.15-as-read** (2026-10-10): what the pinned `web-serial-polyfill` (`dist/serial.js`) actually does, which `CDC_CAPABILITIES` rests on. Framing is real: `open()` rejects anything outside Web Serial's data bits/stop bits/parity and sends the rest in `SET_LINE_CODING` with the CDC encodings, failing the open on a non-`ok` status. Several things differ from our chip drivers, none of them fixable without forking the module. `open()` raises DTR by itself right after the line coding, before the bridge applies the radio's own lines, and `close()` drops both lines. `SET_CONTROL_LINE_STATE` results are not checked, so a refused line change passes silently. Bulk OUT checks `status` but ignores `bytesWritten`, so a short write is truncated silently, which `writeBulkOut` (`web/js/webusb-transport.ts`) guards the chip drivers against. Bulk IN has one transfer per pull, sized up to the stream's desired size rounded to whole packets (256 bytes on a 64-byte endpoint), with no pipeline and no `clearHalt`: a stall errors the stream until reopen. There is no `getSignals()`. It has an in-place `reconfigure()`, which the wrapper does not use. `tests/e2e/web-serial-polyfill.mjs` loads the CDN module in Chromium and pins the line coding and line-state requests against a fake CDC device; no CDC adapter has been measured.
- **android-claim-after-close-race** (2026-10-11): on Android Chrome, a CDC device reopened right after `close()` can have `claimInterface` refused with `NetworkError` ("Unable to claim interface"): Android releases the previous claim asynchronously. Seen on a Raspberry Pi Debug Probe (0x2e8a:0x000c) through the polyfill in the loopback suite, which reopens per baud pass: failures alternated (38400 and 57600 failed, 115200 opened, its once-cases failed, the 9600 reopen opened), and teardown reported no close failure. The polyfill stringifies the error (`Error setting up device: NetworkError: ...`), so `CdcSerialPort.open()` recognizes the refusal by text and retries it after 50/100/200/400 ms (`CDC_CLAIM_RETRY_DELAYS_MS`), then throws the named busy-interface error. The same race can hit a clone, because `reconfigure: "reopen"` close+opens on every mid-clone re-rate or reframe. Not yet re-measured on hardware with the retry in place.
- **debug-probe-drops-at-115200** (2026-10-11): a Raspberry Pi Debug Probe on native Web Serial (macOS) lost 15 of 16384 bytes in the loopback suite's large single-write case at 115200 and passed every case at 9600. - **ftdi-baud-request-by-family-is-unit-tested-not-measured** (2026-10-13): the FTDI driver now picks its `SIO_SET_BAUD_RATE` encoding from bcdDevice, as libftdi does (issue #108). Issue #108 said an FT232H got the wrong rate. That overstated it: without wIndex bit 9 a hi-speed part runs on the same 3 MHz base, and usb-serial-for-android drives every FTDI part that way. What the old encoding got wrong on those parts was the wIndex layout. The reference drivers disagree on wIndex for two families, and the driver follows libftdi for both. On the FT2232C, the kernel and usb-serial-for-android put the port number in the low byte and bit 16 at bit 8, but libftdi does neither. On FT-X, the kernel adds port 1 and the other two send bit 16 alone. The FT-X layout works on an FT231X. No hi-speed, AM or FT2232C part has been tried.
- **serial-transport-contract** (2026-10-07): get `SerialPortMock` from `serialport`'s re-export. `@serialport/binding-mock` is only a transitive dependency, so tests must not import it directly.

Results of `specs/SerialBridge.tla` (TLC 1.8.0, two port objects, five bridge calls). None of these has been seen on hardware.

- **serial-bridge-model-holds-on-the-reopen-route** (2026-11-22): with `reconfigure: "reopen"`, every transport promise settling and a lost device staying gone (`SerialBridge.cfg`), all nine properties hold over 34,819 states: one loss report per connection, streams only on the held port, no null `this.port` dereference, no write to a dropped port, no silent drop, no leaked open port, every call returns, every loss reported.
- **serial-bridge-model-holds-on-webbluetooth** (2026-11-22): WebBluetooth (`SerialBridgeBluetooth.cfg`, 14,427 states) holds all nine as well. - **serial-bridge-in-place-reconfigure-outlives-the-port** (2026-11-22): node-serialport only (`tests/support/node-serial-port.mjs`, the CLI and the test harness), in two windows. (1) The read loop stops while `port.reconfigure()` is pending; the bridge reports `read-stopped` and lets go of the port, then the reconfigure resolves and `_reopenPort()` returns as if it had worked. Whether serialport's `update()` can resolve once the handle is closing is untested; the model assumes it can (`ReconfigureOutlivesClose`). (2) `resetBuffers()` awaits a real flush (`discardInput()`), and the port can be lost meanwhile, even when `prepareClone()` changes no setting; the flush completes before the teardown's close starts, so this one does not depend on serialport. Either way `prepareClone()` then reads `this.port.capabilities` with `this.port` null: a `TypeError`, not "Port is not connected.". Through window (1), `open()`'s reuse path also sets `_announcedOpen` for a port the bridge no longer holds, answering "Reopened at … baud". `tsc` cannot see this, because it keeps the narrowing of `this.port` across an `await`. The todo tests at the end of `tests/webusb/port-loss.mjs` replay both windows against the real bridge: two replay window (1), with a fake whose reconfigure resolves after the close, and fail both ways; one replays window (2) on the Web Serial route, with a flush that resolves after the loss.
- **serial-bridge-reopen-revives-a-lost-port** (2026-11-22): on the "reopen" route a disconnect can land while `_reopenPort()` awaits the reader's cancel, when the notifier is still armed. `_handleTransportDisconnect()` tears the port down and reports it. If `port.open(next)` on the same object then succeeds (the device came back), `_reopenPort()` takes streams on the port the bridge dropped: it stays open with its streams locked, `writeBytes()` (which checks only `this.writer`) writes to it, and `reconfigure()` reports success. Whether a real transport's object reopens after its device returns is untested. `SerialBridgeReplug.cfg`: StreamsOnHeldPort, NoLeakedPort, NoWriteToUnheldPort, NoNullDeref, NoSilentDrop.
- **serial-bridge-hung-close-blocks-the-python-thread** (2026-11-22): `_losePort()` reports before it awaits the transport's close, but its callers still await it (`close()`, `open()`'s teardown, the failure paths of `applyBaudRate()` and `reconfigure()`), and `_reopenPort()` awaits `port.close()` itself. When the hung close is `_reopenPort()`'s, the notifier was disarmed as the close started, so an unplug is never reported either.   - **V8 flags given to `node --test` do not reach the per-file child processes**, so the old flag on `test:channels`/`test:settings` was always a no-op. To disable a V8 feature for a test, run the file directly (as `tests/channels/no-jspi-runtime.mjs` does).

## TypeScript and type checking

- **sources-are-typescript-run-by-stripping** (2026-10-09): what the conversion taught:
  - Node's stripping replaces annotations with whitespace, so line/column numbers are unchanged and V8 coverage measures the `.ts` files with no source map (coverage figures moved by tenths of a point). dist/ kept its shape: 12 JS files, ~460 KB.
  - **`node --check` does not reliably strip types**: under `"type": "module"` it parses as CommonJS first and retries as stripped ESM only when the first error looks like module syntax, so a file whose first error is a type annotation fails. Hence `check:syntax` covers only `.mjs`.
  - `rewriteRelativeImportExtensions` is the alternative to `allowImportingTsExtensions` only for a project that compiles to `.js`.
  - Under `useDefineForClassFields`, redeclaring an inherited property (an `Error` subclass's `name`) shadows the prototype's, so inherited properties are not redeclared.
  - Dead code left alone: `web/js/ui/serial-actions.ts` logs `IDENT ${result.ident}` after a download, but no Python download result carries `ident`.
- **tsc-runs-two-projects-because-node-types-are-global** (2026-10-08): `scripts/tsconfig.json` includes only `web/js/types/browser-globals.d.ts`, because including `web/js/types/` whole pulls in `ui-context.d.ts`, and through it every UI module, into the Node check.
- **typescript-7-ships-tsc-as-a-native-binary** (2026-10-08): `typescript@7` is the Go port with no JavaScript API. The `typescript` package is a launcher; the compiler and its `lib.*.d.ts` live in a per-platform optional dependency (`@typescript/typescript-<platform>`), so an install with `--omit=optional` has no `tsc`. Look for lib files under `node_modules/@typescript/`, not `node_modules/typescript/lib`.
- **strict-landed-with-the-typescript-conversion** (2026-10-08): `tests/` is excluded from tsc because, checked under the scripts config, it has hundreds of errors, nearly all where fakes stand in for DOM and USB types.

## Process

- **dom-elements-are-a-checked-contract** (2026-07-27): leftover drift: `serialTxRx` in `RUNTIME_METHODS` (`web/js/runtime-rpc.ts`) has no caller, and its `#serial-transaction` markup is gone.

- **worktree-needs-submodule-init** (2026-07-27): a fresh worktree has an empty `chirp/`, so every Pyodide-backed test fails with `Invalid CHIRP source dir`, which looks like a regression. `git submodule update --init` is fast because it reuses `.git/modules/chirp`. A worktree's `chirp/` can also start at a commit other than the pin (`git status` shows `M chirp`, `git submodule status` a leading `+`), with the pin not yet fetched; the same command fetches and checks it out (2026-10-30).
- **worktree-borrows-the-parent-node_modules** (2026-09-24): worktrees under `.claude/worktrees/` resolve `node_modules` by walking up to the parent checkout. A probe script must live inside the worktree (one in `/private/tmp` gets `ERR_MODULE_NOT_FOUND`), and a dependency bump in the parent changes what every worktree tests against. tsc does not walk up for a `paths` entry: `tsconfig.json` maps the Pyodide CDN URL to `./node_modules/pyodide/pyodide.d.ts`, so `npm run check:js` (and `npm test`) fails in a fresh worktree with TS2307 on `web/js/runtime-rpc.ts` until `node_modules` is symlinked in from the parent (2026-10-30).
- **asdf-python-unset** (2026-07-23): `python3` depends on the machine having an asdf Python; the fallback is `/usr/bin/python3 -m compileall -q web/python`. Adding python to `.tool-versions` is not free, because the workflows feed that file to `actions/setup-node`.
