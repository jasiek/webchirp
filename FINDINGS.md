# Findings

Durable, non-obvious facts about CHIRP, the browser runtime, and the project's infrastructure.
Grouped by topic; each entry starts with a **bold slug** (grep target) and carries its discovery date.
Narrative/debugging history lives in git log — record only the rule, the mechanism, and the pointer.
Prune entries when the code or infrastructure they describe changes.

**When a test pins a finding, the test owns it.** A suite that re-proves a claim on every run is a
better record than a paragraph that cannot fail, so an entry whose every claim is asserted somewhere
in `npm test` is reduced to a line in its section's *Pinned by tests* list; the mechanism lives in
that test's own header. What stays in prose is what no test can assert: upstream defects we route
around, external API behaviour, browser and platform constraints, and rules about work not yet done.

Corpus counts (image totals, driver/class counts) are measurements against one CHIRP submodule pin —
they are stated with the date they were taken and are expected to drift on the next bump; the method
that produced them is the durable part. All counts below were re-measured on **2026-08-27** against
CHIRP `80d93fe5`.

## CHIRP / Pyodide runtime

- **no-jspi-browsers-fail-init-as-unavailable** (2026-08-19): every non-preseeded driver import goes `ChirpCdnFinder` → `_await_js` → `pyodide.ffi.run_sync`, which needs WebAssembly JSPI — and on a browser without it (Firefox before ~152, current Firefox ESR, Safari) the failure surfaces as *total* init failure, not a degraded catalog: `ui.js init()` loads the static catalog, but a subsequent driver-backed load throws, and the catch puts "Unavailable" in the selected-radio readout and leaves the sidebar disabled (before 2026-09-06 the throw came from `loadSelectedRadioMetadata()` on the auto-selected default `iradio_uv_5118`, which is not in `CORE_CHIRP_RELATIVE_FILES`; nothing is auto-selected now, so on that browser the first failure is whatever radio the user searches for) — the app looks like it never loaded even though the catalog step succeeded. Reproduce on any Firefox by flipping `javascript.options.wasm_js_promise_integration` to false (headless + `browser.dom.window.dump.enabled` makes this scriptable); Firefox 152 has JSPI on by default *and* ships native `navigator.serial`, so current Firefox boots fully. `run_sync` fails as `RuntimeError: WebAssembly stack switching not supported in this JavaScript runtime`; until 2026-09-06 `find_spec` swallowed that and the debug panel showed only a generic runtime traceback, and since issue #100 the finder logs the cause plus its traceback and re-raises it as an `ImportError` naming the module and source path — also check `pyodide.ffi.can_run_sync()` when triaging. Since 2026-08-19 `app.js` detects JSPI up front (`typeof WebAssembly.Suspending`/`.promising`) and the unsupported-browser overlay explains the gap before the traceback, but the underlying init failure is unchanged. Issue #1 ("only 14 radios" on Firefox/Safari) was the same root cause wearing the pre-static-catalog symptom.
- **static-driver-catalog** (2026-06-23, counts refreshed 2026-08-27): `list_registered_radios()` in Pyodide imports all 192 CHIRP drivers, each triggering a blocking jsDelivr fetch via `ChirpCdnFinder` — so the catalog is precomputed at build time (`scripts/build-catalog.mjs` → `web/radio-catalog.json`, 554 radios). The runtime accepts it only when its `chirpRevision` exactly matches `DEFAULT_CHIRP_REVISION` (`web/js/python-sources.mjs`), falling back to live enumeration otherwise; `build:catalog` refuses to emit on a drifted submodule. Pyodide boots lazily on first radio selection / CSV / serial action.
- **catalog-aliases-are-the-only-handle-on-rebadged-radios** (2026-09-06): each catalog entry may carry `aliases`, the `{vendor, model, variant}` identities from the driver's `ALIASES` plus the class's own (`runtime_bridge.py:359-392`, emitted only when there is more than one). This is not decoration: a driver is filed under **one** vendor, so `uv5r:BaofengUV5RGeneric` is the driver for Retevis RT5R/RT5RV/RT5, Rugged RH5R, Radioddity UV-5R EX and Ansoko A-5R, and none of those vendors exists anywhere else in the catalog. While the sidebar had a make dropdown the aliases were unreachable but the omission was invisible — the vendor list came from `r.vendor` alone, so a Retevis owner simply did not find themselves there either. Search-only selection (2026-09-06) makes it decisive: the search haystack has to include the alias identities or a rebadged radio is unfindable by the name printed on it, and the suggestion has to *say* which alias matched, or a query for "retevis" returns a list of Baofengs with no explanation. `image-metadata` matching reads the same list for a different purpose — see **wrong-match-is-worse-than-no-match**, where alias identity is what makes `rclass` unusable as a primary key.
- **gettext-builtins-come-from-wxui** (2026-07-27, trimmed 2026-08-07): CHIRP drivers call `_()` and `ngettext()` as *builtins*, but the only place that installs them is `builtins._ = wx.GetTranslation` inside `chirpmain()` (`chirp/chirp/wxui/__init__.py:186`) — a frontend we never load, so otherwise-fine driver code raises `NameError: name '_' is not defined`. `runtime_bridge.py` installs passthrough builtins before importing `chirp`, guarding on `callable()` rather than `hasattr` because a REPL binds `builtins._` to the last result (`runtime_bridge.py:25`). Grep hits are spread across 76 runtime-importable modules and grow with every submodule bump — treat this as runtime-wide setup, not a per-driver patch.
- **upstream-tests-skip-power** (2026-07-29): CHIRP has no byte-level image round-trip test at all — `grep save_mmap\|get_packed` over `chirp/tests/*.py` is empty at the top level (the hits are all under `tests/unit/`: bitwise, alinco clone, chirp_common). The closest is `test_brute_force.py::test_get_set_all`, which does `get_memory` → `set_memory` → `get_memory`, and `assertEqualMem` (`chirp/tests/base.py:160`) skips `power` with a bare `# FIXME`. So driver-level power round-trip defects are invisible upstream — `ftm7250d.FTM7250Radio` inverts Hi/Low on that exact sequence with no webchirp code involved. Don't expect an upstream oracle for anything power- or image-fidelity-related; also note `chirp/tests/driver_xfails.yaml` carries only `TestCaseBruteForce` entries, and `xfails.txt` is comments only with no test entries, so every image in `tests/images/` is expected to detect and load cleanly.
- **idrp-never-registers** (2026-07-30, narrowed 2026-08-07): `idrp.IDRPx000V` has no `@directory.register` decorator upstream, so it does not appear in `DRV_TO_RADIO` even in desktop CHIRP. It is one of the two drivers the pyserial shim exists for, which makes it look like a shim bug — fixing its import cannot add it to the catalog, and its absence there is upstream-correct.
- **blank-instances-misreport-state** (2026-03-14, widened 2026-07-30): a driver instantiated with no image — `radio_cls(None)` — is not a smaller version of a parsed one, it is a *differently behaving* one, and this bites in two places. **Settings**: many drivers only materialize settings from a cached clone image, parsed file image, or live session, so `get_settings()` on blank state can throw — treat settings as unavailable until backing state exists, and when instantiating for metadata enumeration fall back to `radio_cls("")` if `radio_cls(None)` fails (`_driver_features()`, `runtime_bridge.py:423`). **Features**: `get_features()` differs too — `retevis_rt98.Rt98Radio` advertises only the PMR level (`Low` = 0.5W) blank and the full `Low`/`Mid`/`High` set (`Low` = 5W) once an image is parsed, so a power label resolved against blank features picks the wrong wattage. `_driver_features()` prefers `LAST_IMAGE_BY_DRIVER` and falls back to a blank instance.
- **skip-immutable-on-apply** (2026-03-14): replaying serialized values onto a fresh settings tree includes immutable fields, which drivers reject with `This value is not mutable` (`chirp/chirp/settings.py:85`); bridge-side apply logic must skip non-mutable CHIRP values entirely (`_setting_value_is_mutable()`).
- **upstream-get-max-defect** (2026-03-14, still present 2026-08-07): vendored CHIRP's `RadioSettingValueFloat.get_max()` has no `return` (`chirp/chirp/settings.py:203`), so it returns `None`; serialize float bounds via the `_max` instance field fallback.
- **parse-freq-negative-defect** (2026-07-30): upstream `chirp_common.parse_freq()` mishandles negative decimals — it splits on `.` and sums `int(mhz) * 1e6 + int(khz)`, so the fractional part is always added: `parse_freq("-0.600000")` → **+600000** (`int("-0")` is 0) and `parse_freq("-5.600000")` → −4400000 instead of −5600000. Harmless for `to_csv`-derived rows (no driver emits negative offsets; they normalize to duplex `+`/`-`), but a hand-typed or imported negative offset is silently corrupted. The old `to_MHz(float(text))` path was sign-correct but truncates — neither upstream parser handles both; validate/reject negative offsets before parsing if they ever need to round-trip.
- **synchronous-python-can-drive-progress** (2026-07-30): a plain `for` loop inside one `runPythonAsync` *can* animate browser UI, which looks impossible and is why the driver sweep shipped silent at first. Every CHIRP import suspends the interpreter on a CDN fetch through `ChirpCdnFinder`'s JSPI `run_sync`, so the JS event loop runs between iterations and anything the loop wrote to the DOM paints — the same mechanism that lets CHIRP's synchronous clone loops drive `#clone-progress` via `serial_progress`. So reach for a callback argument (`import_all_driver_modules(names, progress_cb)`) before restructuring a loop into per-item RPCs; the latter would pay a full call-queue round trip per module for no benefit — but clear the `pyodide.globals` slot afterwards (`runtime-rpc.js:149`), or the JS callback outlives the operation that needed it. The reverse also holds — a Python loop that never suspends will not paint, so this is a property of the I/O, not of Pyodide.
- **all-driver-import-mechanics** (2026-07-30, re-measured 2026-08-27): the sweep is one synchronous Python loop in a single `runPythonAsync` (~1.8 s in Node off the local checkout; ~20 s in-browser, where each module is fetched individually from jsDelivr), cached per session as a promise that resets on failure so a later load retries instead of caching the wreck. `import_all_driver_modules()` tolerates per-module failures, surfacing each as `DRIVERS SKIP <module>: <error>`; all 192 modules import and 554 radio classes register at this pin, so the skip list is empty — keep reporting it anyway, because importability cannot be judged by grepping for `import serial` (`hf90`/`tmv71_ll` have function-scope imports that are harmless) and the next submodule bump can reintroduce a failure silently. `scripts/build-catalog.mjs` calls the same function so the catalog's "not importable, absent from catalog" warnings and the runtime's skip lines can never diverge.
- **transport-disconnect-events-name-different-things** (2026-08-24): the two transports report an adapter going away in shapes that share nothing. Native Web Serial fires `disconnect` **at the `SerialPort` object**, bubbling to `navigator.serial`, so `event.target` is the very port `requestPort()` returned and object identity settles the match. WebUSB fires at `navigator.usb` and names the device in `event.device`, which is a `USBDevice` — not the Web Serial-shaped port the app holds. Our four chip drivers keep that device as `port.device`, so identity still works there, but the CDC polyfill's `SerialPort` keeps it private, leaving the vid/pid from `getInfo()` as the only handle — which cannot tell two identical adapters apart, and is why the id comparison is a fallback rather than the primary test. Neither event covers the *radio* being switched off behind a cable that stays enumerated: the port remains open and the read loop just goes quiet, so that case is still only visible as a clone timeout.
- **shim-owes-pyserial-return-values-not-just-methods** (2026-09-05): `WebSerialPipe` is duck-typed against pyserial, and matching the method *names* is not enough — drivers read the return values, so a method that works for 550 radios can be unusable for one. `write()` returned `None` where pyserial returns the byte count, and `puxing_px888k.pipewrite` (`chirp/chirp/drivers/puxing_px888k.py:576`) checks `if n is None: raise`, so the PX-888K aborted on its first handshake write and could never clone (issue #79). The same call in `tk11` (`:614`, `:655`) checks `bytes_written == 0`, and `None == 0` is `False`, so the identical violation was silently harmless there — which is why this survived: how loudly a broken contract fails depends on which comparison the caller happened to write, not on how broken it is. Find the rest by grepping driver code for *consumers* of shim return values, not for method names. **Still open from that sweep:** `in_waiting` is hardcoded `0` (harmless — `retevis_c2:483,523` only uses it to drain garbage and to log diagnostics), but the legacy alias `inWaiting()` is not defined at all, so `anytone778uv:345` raises `AttributeError` inside its read loop. Unverified against hardware; adding the alias would turn that into a 0.5 s silent timeout instead, so it needs a real `in_waiting` to be worth doing.
- **the-pipe-is-reconfigured-mid-clone** (2026-09-05): the sibling of **shim-owes-pyserial-return-values-not-just-methods**, on the argument side rather than the return side. CHIRP drivers do not just read and write `self.pipe` — they *reconfigure* it mid-clone, so `WebSerialPipe` (`web/python/runtime_bridge.py`) has to answer for every attribute they touch, in pyserial's exact spelling. Two rules follow. **Optional arguments are part of the signature**: pyserial's `setRTS(level=True)`/`setDTR(level=True)` take the level optionally, `thd72.py:480` calls `self.pipe.setRTS()` bare and catches only `AttributeError`, so declaring `def setRTS(self, value)` raised `TypeError` and killed the TH-D72 clone before its first block (issue #77). **A stored boolean is not a line change**: `setRTS`/`setDTR` and the `rts`/`dtr` properties now push to the port through `serial_set_signals` → the `setSignals` RPC, because the initial `_prepare_clone_session()` assertion is the only one the transport used to see. Pipe construction is the deliberate exception — `_new_serial_pipe()` seeds the lines without pushing, leaving `_prepare_clone_session()` to assert them together with the settle delay a radio needs after a level change. **The port configuration is the third case, and it needs a reopen**: `baudrate` and the framing attributes are properties too, pushed through `serial_reconfigure` → the `reconfigure` RPC. The reopen mechanics and why they cost no user gesture are in **baud-rate-is-latched-at-open**; what is specific to doing it *mid-clone* is three things that the clone-*start* re-rate does not need and would be wrong to copy. It **keeps the buffered bytes**, because pyserial reconfigures with `TCSANOW`, which does not flush the input queue — drivers are written against that, and `thd72` reads a byte immediately after switching to 57600, where a clone-start re-rate correctly discards whatever preceded it. Carrying them across is an *ordering* problem more than a copying one, and both ends bite: the buffer must be read only after the reader is cancelled and the loop awaited (earlier, and a chunk completing during cancellation is appended behind the snapshot and dropped), and written back before the next loop starts (later, and a chunk the reopened stream already had ready is overwritten by the bytes being restored). Both windows are inside `_reopenPort()` for that reason, not at its call sites. It **re-asserts DTR/RTS**, because closing a port drops the lines to the adapter's defaults and `thd72` sets the rate and raises RTS two lines apart, so whichever came first would otherwise be undone — at clone start `prepareClone()` sets the lines a moment later anyway. And it **only reopens on a real change**, since drivers assign the rate they already have (`tk8180`'s reset path, a probe loop re-asserting its winner) and a reopen re-initialises the chip. The two entry points therefore share one `_reopenPort()` but not their failure policy, which is the part to keep straight: `applyBaudRate()` tears the session down and reports a lost port, because nothing has transferred yet and a port that cannot carry the clone must stop offering Download; `reconfigure()` puts the previous settings back and keeps the session, because the port itself is fine and a live one lets the user retry without re-picking the device. Neither is advisory the way the control lines are — the radio has already switched by the time the assignment runs, so the error propagates rather than being logged, or it resurfaces as an unexplained read timeout much later. `timeout` needs none of this — `read()` reads it per call.
- **framing-is-set-after-open-but-never-mid-clone** (2026-09-05): the useful half of surveying all 23 `self.pipe.baudrate` assignment sites and their framing neighbours (measured against CHIRP `80d93fe5`). **Every** `parity`/`stopbits`/`bytesize` assignment in a clone-mode driver happens before that operation's first byte — there is not one mid-clone framing change in the tree — but they all happen *after* the port was opened, because the UI connects before the user presses Download. So they are not free either: `tg_uv2p` and `tk8180` want two stop bits, `tk280`/`ft2800`/`tk760g`/`tk8102`/`hg_uv98` want even parity, `ft450d` sets all four, and against a port hardcoded to 8/1/none every one of those is ignored. They ride the same reopen as the rate for exactly that reason — on a transport that can carry them at all, which per **webusb-chip-ports-are-8n1-only** means native Web Serial and the CDC polyfill but none of the four WebUSB chip drivers. Three exclusions are deliberate. `xonxoff` is assigned **nowhere** in CHIRP. `rtscts` appears only at `ft450d.py:504,534`, both `= False`, which is already what `flowControl: "none"` means. And `tk3140.py:49` assigns `pipe.databits`, a typo for pyserial's `bytesize` that is dead on real pyserial too — implementing it would make us diverge from pyserial rather than match it. Two shapes to expect from the drivers that do change rate: **probe loops** that walk four to six rates with I/O between each (`thd72`/`thd74`/`tmv71` `_detect_baud`, `ts480`/`ts590`, `tmd710` via `kenwood_live.get_id`), so a single `sync_in` can reopen the port six times; and `tmd710.py:92`, which logs `pipe.baudrate` with `%i` and would `TypeError` on `None` — the pipe is seeded from the driver's `BAUD_RATE`, which is what keeps it a number. The breadth is wider than the TH-D72 that prompted it: `icf.start_hispeed_clone` switches to 38400 mid-clone for the **11 driver modules** setting `_can_hispeed = True` (ic2200, ic208, ic2300, ic2730, ic2820, icp7, icv80, id31, id800, id880, id5100), in both directions.

- **pyserial-peeks-are-not-free-here** (2026-09-05): `WebSerialPipe` answered `in_waiting` with a hardcoded 0 and had no legacy `inWaiting()` at all, and both halves of that break drivers differently. The missing alias is loud — `anytone778uv.send_serial_command()` calls `serial.inWaiting()` and every clone of an `AnyTone778UVBase` radio (eight catalog entries: AnyTone 778UV, Retevis RT95, CRT Micron UV, Midland DBR2500, Yedro YC-M04VUS and the three VOX variants) died with `AttributeError` on its first command. The constant 0 is the silent half: a driver that only reads when `in_waiting` is non-zero reads *nothing* and hands back an empty response with no error, so adding the alias without a truthful count just converts the crash into a mystery timeout. Reporting the real count needs care in the other direction too — pyserial answers from a local kernel buffer, so drivers treat the peek as free and poll it in tight loops (this one spins for 0.5 s per clone block), while here each peek is a JSPI round trip out of Pyodide; an honest non-blocking answer turns one 16-byte block read into thousands of round trips. `BrowserSerialBridge.inWaiting(waitMs)` therefore parks on the same read event `readHex()` uses when the buffer is empty, so it settles the instant bytes land and only an *idle* line costs a wait (`IN_WAITING_WAIT_MS`, 40 ms — it has to stay well under the driver's own 0.5 s deadline). That fix alone did not make those eight radios clone — `do_download()` documents that the radio is already in programming mode "because of detect_from_serial()", which webchirp did not call; see **detection-is-part-of-the-clone-not-a-lookup** for the other half (issue #81).

- **detection-is-part-of-the-clone-not-a-lookup** (2026-09-05): `detect_from_serial()` reads like an optional "which variant is this?" convenience, and treating it as one is why webchirp skipped it entirely for the whole of its clone flow (issue #81). It is not a lookup — for several driver families it is *the first leg of the clone protocol*. `ga510.detect_from_serial` sends the program magic through `start_program()`, and its `do_download()` opens with the comment "No `start_program()` here because it was done in `detect_from_serial()`"; `tdh8` says the same ("Radio must have already been ident’d"), and so do `anytone778uv` and `tdm11`. Skip it and the radio is never asked to enter programming mode, so the download reads nothing and reports a timeout that looks like a cable fault. `leixen`, `h777` and `uvk5` use it the way the name suggests, to pick the subclass whose codeplug layout matches — `uvk5` even falls back to a restricted class on unapproved firmware. Three consequences shape the fix. **Detection and the clone must share one pipe object**, because the handshake’s state lives on the wire, not in the returned class — `_create_radio_for_serial()` builds the pipe, detects on it, then instantiates the detected class with that same pipe. **`NotImplementedError` is an answer, not a failure**: `DetectableInterface.detect_from_serial` raises it for the ~547 drivers with nothing to detect, so it means “use me as selected”, while `RadioError` must propagate — a driver reporting an unexpected response is telling you the clone will not work. **Upload does not re-detect**: CHIRP calls it only in the download path (`chirp/wxui/clone.py:803`), because the class that read the image is the one that writes it back and `ga510.do_upload()` sends its own `start_program()`. That last point is what makes the detected class *state* rather than a local: the cached image belongs to the variant that downloaded it, so re-parsing those bytes with the parent class the user picked in the UI decodes the wrong fields. `IMAGE_CLASS_BY_DRIVER` tracks it alongside `LAST_IMAGE_BY_DRIVER`, and the two are one fact split across two dicts, so all five writers go through `_cache_driver_image()` and it serializes *before* recording either — record the class first and a `save_mmap()` failure leaves the **previous** download's bytes tagged with this radio's class, which is worse than not caching at all because nothing downstream can tell. The consolidation also caught `load_image_base64()`, where `directory.get_radio_by_image()` had already been resolving to a `DynamicRadioAlias` subclass that the cache then forgot. Checked against the current submodule pin: no registered class has detected models without its own `detect_from_serial`, so the base method’s `assert detected is None` cannot fire.
- **errors-lose-their-identity-crossing-pyodide** (2026-09-06): a JS rejection that Python awaits comes back to the UI as *text*, not as an object. `serial_open` rejects, Pyodide wraps it as a `JsException`, `runPythonAsync` raises a `PythonError` whose message is the whole traceback, and `wrapRuntimeMethod` (`web/js/runtime-rpc.js`) rethrows `new Error(detailedError)` — so `error.name`, `instanceof` and any custom property are gone by the time a caller could branch on them, and only the message survives. `classifyErrorKind()` (`web/js/ui/analytics.js`) always worked this way, matching substrings against the whole detail rather than reading a field, and that is the general rule: **anything the UI must recognise about a failure has to be spelled into the message where the failure is raised.** The case that forced it: dismissing the browser's port chooser rejects with `DOMException NotFoundError`, which is a user decision, but by the UI it was indistinguishable from an adapter that would not open — so a cancelled Connect was reported as a Python traceback, and since the app has no status line at all (`setStatus()` writes into the same Debug Output panel, `web/js/ui/debug-log.js`) pressing Connect and then Cancel looked like a button that did nothing. `web/js/serial-errors.js` is now the one place that names that outcome, in a sentence that survives the round trip; its wording has to keep containing "No port selected", because that substring is what `classifyErrorKind` matches to report `error_kind=port_not_selected`.

*Pinned by tests:*
- All Pyodide-backed RPCs go through the FIFO call queue (`web/js/call-queue.mjs`) — concurrent RPCs re-execute a suspended driver import (`Duplicate radio driver id`) and clobber the shared `_sel_*` globals; UI loads carry monotonic tokens on every selection transition and apply metadata/settings atomically, so neither half of a stale load can overwrite a newer selection — `test-call-queue.mjs`, `test-driver-import-race.mjs`, `test-ui-radio-loading.mjs`.
- The gettext builtins are installed, pass strings through untranslated, and come from the runtime rather than from loading `chirp.wxui`; no radio's settings fail on a missing name — `test-gettext-builtins.mjs`, `test-radio-settings.mjs`.
- Drivers importing pyserial at module scope (`tg_uv2p`, `idrp`) import and register in Pyodide, the shim `Serial` refuses construction with a clear error, and `WebSerialPipe.write()` returns the byte count so `puxing_px888k.pipewrite` accepts it — `test-pyserial-shim.mjs`.
- The pipe's control lines default to asserted, reach the transport on every driver-initiated change, and stay off the port while the constructor seeds them; a port that cannot set DTR/RTS logs and continues instead of failing the clone — `test-pyserial-shim.mjs`, `test-serial-control-lines.mjs`.
- A driver's baud-rate and framing changes reopen the same port with the merged options, keep the bytes buffered before the switch, re-assert the control lines the close dropped, skip the reopen when nothing changed, and restore the previous settings when the new ones are refused — sharing one reopen with the clone-start re-rate without inheriting its teardown-on-failure; the pyserial framing values with no Web Serial equivalent are kept for read-back without being pushed — `test-serial-reconfigure.mjs`, `test-pyserial-shim.mjs`. Each assertion is checked against the defect it claims to catch: dropping the buffer, the signal restore, the no-change guard or the failed-reopen recovery each fail their own test and no others.
- `in_waiting` reports the bridge's real buffered count under both spellings, and a full AnyTone 778UV clone against a simulated radio returns the radio's bytes and channels — `test-serial-in-waiting.mjs`. Both halves are checked against the defect they catch: dropping `inWaiting()` reproduces the original `AttributeError`, and pinning `in_waiting` back to 0 makes the clone come back empty.
- Serial detection runs before `sync_in()`, on the pipe the clone then uses, and the class it returns is the one that clones and owns the cached image; a driver with nothing to detect clones as selected, and a failed detection handshake propagates instead of cloning blind; and a download whose image cannot be serialized leaves the cached bytes and their class both untouched, checked against the defect by recording the class first — `test-clone-detect-from-serial.mjs`.
- A dismissed port chooser is reported as a cancellation rather than a crash: named at the bridge for both transports and only for `NotFoundError`, still recognisable after the runtime has flattened it into a traceback, still classified as `port_not_selected`, and shown as a sentence that opens the debug panel without becoming the next bug report's title — `test-serial-port-cancel.mjs`.
- A settings tree read from an image can be written straight back for every upstream image that carries one: a settings node is addressed by position rather than by name (CHIRP guarantees neither unique sibling names nor a name-indexable root), values CHIRP could not initialize are skipped rather than replayed as null, and a value equal to the one the driver just emitted is not rewritten — so the read/write asymmetries in `RadioSettingValueString` padding and `RadioSettingValueList` options cannot fail an upload the user never edited — `test-settings-round-trip.mjs`. Each of the four upstream conditions is pinned by its own fixture assertion, so a submodule bump that removes one fails loudly instead of leaving the round-trip test passing vacuously.
- **undecodable-memories-couple-download-to-erase** (2026-09-06): the download and upload loops in `runtime_bridge.py` are coupled through absence, which makes a swallowed read on one side a destructive write on the other. `_radio_rows_from_instance` skips any number `get_memory` raises on, and `_apply_rows_to_radio_instance` treats every valid number *missing from the rows* as a user deletion — so one memory the driver cannot decode used to vanish from the grid and then be erased on the radio at the next upload. The erase half was closed incidentally by PR #123 (issue #83, immutable-policy validation), which made the erase loop read before erasing and skip what it cannot read; the download half stayed silent until issue #82. Both halves now report to the debug panel, grouped by failure reason via `_format_channel_numbers` rather than one line per slot, because `memory_bounds` runs to hundreds of channels and a driver that raises on all of them would bury the panel. Upstream CHIRP takes the other route (`wxui/memedit.py` passes the exception itself into `_refresh_memory`) and renders an error row; we keep the row out of the grid and return the numbers as `unreadableChannels` instead, since a placeholder row would have to survive `normalize_rows` and the upload path without being mistaken for something writable. Reading before erasing is *not* on its own enough to protect the slot: upload and export both discard the downloaded instance and rebuild a fresh radio from `LAST_IMAGE_BY_DRIVER`, so a decode failure that was one-shot or instance-local does not repeat on the instance that erases, and the guard sees a perfectly readable memory missing from the rows. The numbers are therefore recorded at extraction time in `UNREADABLE_BY_DRIVER` (keyed like the image cache, always overwritten so a later clean read drops stale protection) and subtracted from the erase candidates; a row the user does supply for that number still writes, because explicit intent lands in `seen_numbers` and never reaches the erase loop.
- **exception-text-is-an-unbounded-grouping-key** (2026-09-06): grouping per-channel driver failures by their exception text does not bound debug-panel output, because a driver is free to name the memory number or the offending value in the message — CHIRP drivers do — which makes the key unique per slot and turns "one traceback per group" back into one traceback per channel (128 of them for a UV-5R that fails everywhere). `MAX_LOGGED_FAILURE_GROUPS` caps the groups as well, and `_log_grouped_channel_failures` orders by descending channel count so truncation drops the long tail of one-off messages rather than the failure that explains the most channels.
- **rebinding-serial_log-in-tests** (2026-09-06): `seedPyodideRuntime` runs the bridge with `runPythonAsync`, so every bridge name lives in `__main__`'s globals — the same dict `runPythonJson` later evaluates in. `_log_debug` resolves `serial_log` from those globals at call time, so a test can capture debug-panel output by assigning `serial_log = lambda message: ...` at the top level of its probe and restoring it afterwards. Overriding `globalThis.serial_log` from JS after init does *not* work: `from js import serial_log` bound the original function object at import time.

## Channel grid / CSV

- **csv-radio-is-not-a-round-trip-surface** (2026-07-30, trimmed 2026-08-07): `generic_csv.CSVRadio` is CHIRP's import/export vehicle, not a lossless staging format, and three traps follow. **A header-only CSV is not a valid file** — `_load()` raises `InvalidDataError("No channels found")`, so the editor's startup column schema comes from `chirp_common.Memory.CSV_FORMAT` directly rather than from round-tripping one. **`CSVRadio(None)` seeds a non-empty channel 0** at 146.010000/50W, and `_load()` — the path `load_from()` takes — never calls `_blank()`; only the filename path `load()` does. Upstream never trips over it because `wxui/memedit.py` calls `erase_memory(0)` right after constructing its export radio (`chirp/chirp/wxui/memedit.py:2819`); use `_blank_csv_radio()` for any new `CSVRadio(None)`. **`_load()` drops zero-frequency rows**, but drivers do report non-empty memories with no frequency (uninitialised locations in `Icom_IC-W32A`, `Jetstream_JT220M`) and CHIRP exports them, because its export never round-trips through its own parser — so staging rows through a CSV document loses channels the grid shows. `_memories_from_rows()` calls `CSVRadio._parse_csv_data_line()` per row instead, keeping CHIRP's ATTR_MAP converters and its 50W default without the `_load()` filter.
- **csv-export-is-import-logic** (2026-07-30, pointers corrected 2026-08-07): CHIRP's CSV export is not `Memory.to_csv()` on the driver's memories — `_export_to_file` (`chirp/chirp/wxui/memedit.py:2803`) pushes each one through `import_logic.import_mem(...)` (:2827) into a `generic_csv.CSVRadio` and saves that. Three things follow that a rows→CSV writer gets wrong on its own. `CSVRadio.set_memory()` rewraps power as `AutoNamedPowerLevel(dBm_to_watts(float(level)))`, so an exported CSV always holds watts and never a driver label — and `PowerLevel.__int__` truncates the dBm, so converting with `int()` writes a 50W level as `39W`. `_import_tone`/`_import_dtcs` fill columns the source radio does not track separately (rtone→ctone, dtcs→rx_dtcs). And an incompatible memory is logged and written **unconverted**, not dropped. `normalize_rows()` mirrors all of it.
- **dvmemory-to-csv-layout** (2026-07-30): `DVMemory.to_csv()` (`chirp/chirp/chirp_common.py:614`) still emits the pre-RxDtcsCode/CrossMode/Power layout — 18 fields where `Memory.CSV_FORMAT` (:398) has 21 — so zipping it against the headers puts the mode string in `RxDtcsCode` and shifts everything after. CHIRP dodges it by forcing `mem_cls=chirp_common.Memory`; `_row_values_for_csv()` clones DV memories into a plain `Memory` for the same reason. Call signs are dropped either way — CHIRP's CSV export drops them too.
- **power-labels-beat-watts-in-rows** (2026-07-30, re-measured 2026-08-27): rows and the grid carry power as the driver's *label*, not watts, and that is the right way round in both directions. Of 554 driver classes, 455 advertise power levels and **zero** advertise two levels with the same label — but **8** collapse onto the same watt string once `dBm_to_watts()` rounds to 1 dp (`retevis_rt21.RT619Radio`/`RB628BRadio`, `radtel_t18.RB619Radio`/`RB629Radio`/`H777HPMRRadio`, `bf_t8.RetevisRB627B`, `retevis_rb28.RB628Radio`, `radioddity_gm30.RadioddityMU5`; the `mml_jc8810` family stopped colliding at the 2026-08-27 bump), so watts in a cell would be ambiguous where a label is not. It also matches CHIRP, which shows watts only for `has_variable_power` radios (`ChirpVariablePowerColumn`, `chirp/chirp/wxui/memedit.py:422`, chosen at :1432) and labels for the rest. The residual cost of labels: some driver modules define a second, *unadvertised* level list keyed by band (`vx6`/`vx7.POWER_LEVELS_220`, `ft90`'s VHF/UHF pair), so a label under-determines watts for channels outside the primary band and our CSV writes the advertised value (VX-6 220 MHz: `5.0W` where CHIRP writes `1.5W`). Radio *writes* are unaffected — `vx6.set_memory` re-resolves power from the frequency. `_power_level_watts()` publishes the label→watt mapping so the grid can show it as a hover legend; that legend is column-level for the same band-keyed reason — `valid_power_levels` cannot say which list a given channel's level came from.
- **set-memory-is-not-a-tone-backstop** (2026-07-29, split out 2026-08-07): dropping `Memory.really_from_csv()` gave away one validation nothing else performs — it rejected rtone/ctone outside `TONES` and dtcs codes outside `DTCS_CODES`, and many drivers encode these raw (e.g. `int(mem.ctone * 10)`) without checking. So `set_memory()` is *not* a backstop for tone values, and external CSV fed through `npm run radio:write` can plant a nonstandard tone in the image silently. The UI's enum dropdowns constrain the browser path; the CLI path has nothing.
- **rows-not-bytes-for-round-trip** (2026-07-29): byte-identity is a poor oracle for a load → export cycle — most upstream test images re-export with every row identical but different bytes, because padding and unused regions move. Compare rows field by field (`scripts/test-channel-round-trip.mjs`, a set of targeted per-defect image lists rather than a full corpus walk); treat byte-identity as a bonus, not a requirement.
- **location-is-a-memory-slot-not-a-row-index** (2026-09-05): a channel's `Location` says which memory it occupies, and nothing in the editor may derive it from the row's position. Two facts make that load-bearing. Codeplugs read from a radio are routinely **sparse** — `chirp/tests/images/Baofeng_UV-5R.img` fills 37 of its 128 slots (0-1, 25-31, 50-66, 80-86, 124-127), and the slot numbers themselves carry meaning the grid cannot see, because scan lists and the channel dial address memories by number. And **147 of the driver `memory_bounds = (` call sites number memories from 1**, against 65 from 0 (measured 2026-09-05 against CHIRP `80d93fe5`), so 0 is not a safe floor for an allocation: `uv5r.BaofengUV5R` is `(0, 127)` at `chirp/chirp/drivers/uv5r.py:880` while `BaofengUV6Radio`, three classes down the same module at :2302, is `(1, 128)`. Allocation goes through `reconcileLocations()` (`web/js/ui/channel-table.js`), the single call every row operation and every load makes after touching `state.currentRows`: `assignFreeLocations()` leaves each row holding a valid unclaimed Location where it is and hands the rest the lowest free slot inside the driver's bounds — read off the Location column's `min`/`max`, which `get_radio_column_metadata()` fills from `memory_bounds` — then `sortRowsByLocation()` restores the grid's ordering invariant: **row order is memory order, always**. That invariant was free while Location *was* the row index and has to be maintained explicitly now that it is not, because a row inserted at the end of the array can be handed memory 11. Rows with no usable Location sort last, keeping their arrival order, and the upload preflight is what reports them. Because row objects carry their own identity, operations reselect by identity (`selectRowsByIdentity`) rather than by the index they spliced at, and the `__geo` sidecar (`web/js/row-geo.js`) rides along untouched. Move Up/Down is the one operation that reorders: it rotates the channels through the slots already in use rather than renumbering, so the occupied set never changes and the re-sort is a no-op. Two consequences of the invariant that are easy to get wrong and are each pinned by a test. **Loading calls `sortRowsByLocation()` alone, never `reconcileLocations()`** — a file's Locations are the user's data, so a duplicate or out-of-bounds one must survive to the upload preflight rather than being silently reassigned on the way in. **Paste targets consecutive memories from the selected channel's memory, not consecutive rows**: on a sparse codeplug the rows below memory 26 may be 124 and 127, so walking rows scatters a pasted block across the radio and clobbers distant channels the user never aimed at.

- **grid-cost-is-option-lists** (2026-07-27): the channel grid's DOM size is dominated by `<option>` elements, not cells. Every enum cell carries the driver's full option list (rToneFreq ~50, DtcsCode ~100+), so a UV-5R row is ~380 elements, not 17 — a 503-channel codeplug is ~191,000 elements and rebuilding it took seconds, which every insert/remove/move/paste paid. `web/js/ui/channel-table.js` virtualizes the grid: only the rows overlapping `#mem-table-scroll` (plus overscan) exist, row elements are recycled by rebinding values rather than rebuilt, and cell events are delegated to the tbody. Two consequences to keep in mind: browser find-in-page and Tab reach only the rendered rows, and anything reading the grid from the DOM must select `tr[data-row-idx]` (spacer rows stand in for the rest) instead of indexing `tbody.children`.
- **markup-defaults-are-the-boot-state** (2026-08-02): the first `table.render()` runs at the *end* of `init()` (`web/js/ui.js`), after Pyodide boots and the catalog, driver metadata and settings all resolve — so whatever `index.html` ships is what the user looks at for the whole boot, and it is also what they are left with if `init()` throws into its catch branch. Markup defaults for anything the JS toggles must therefore be set to the *pre-runtime* state, not the post-render one.
- **file-drop-wiring** (2026-07-27, trimmed 2026-08-07): two requirements of drag-and-drop loading (`web/js/ui/codeplug-io.js`) that no test can see. The drop overlay must stay `pointer-events: none`, otherwise the element that appears under the cursor becomes the drag target and cancels the drag it is announcing. And files are routed by extension, not MIME type: browsers report `.img` as `""` or `application/octet-stream` depending on platform, and CSV as anything from `text/csv` to `application/vnd.ms-excel`.

## Radio images (.img) & metadata

- **radio-load-marker-means-schema-and-settings** (2026-09-05): `lastLoadedRadioKey` may only identify a radio after both its column metadata and settings state have been applied. An image import is a complete radio load too: after it selects the detected driver, loads that driver's metadata, and installs the settings serialized in the image, it must update the marker or re-selecting the pre-image radio is mistaken for a no-op and leaves the image driver's schema/settings active. Moving the marker into `loadSelectedRadioMetadata()` is unsafe even though it appears more general: metadata and settings resolve concurrently on dropdown changes, so marking the radio after metadata alone creates a rapid-switch window in which a return selection short-circuits without invalidating another radio's in-flight settings response.
- **wrong-match-is-worse-than-no-match** (2026-07-23, reduced to its invariant 2026-08-07): `directory.get_radio_by_image()` only searches drivers already in `DRV_TO_RADIO`, and the browser imports drivers lazily — so `handleLoadImage` parses the metadata trailer first (driver-free), resolves the module via the catalog, imports it, then runs detection; when nothing resolves, `ensureAllDriverModules()` imports every driver so `match_model()` byte-sniffing can run. **The governing invariant: a resolved-but-wrong match is worse than no match, because it suppresses the sweep.** The matcher must therefore be at least as precise as the `get_radio_by_image()` it front-runs, comparing VENDOR/MODEL/VARIANT across `rclass.ALIASES + [rclass]` (`chirp/chirp/directory.py:202-204`) and declining rather than guessing when several candidates survive. Two consequences that are easy to undo: `rclass` cannot be the primary key, because CHIRP stamps the synthetic `DynamicRadioAlias` (directory.py:206) whenever detection went through an alias; and `variant` `None` (not recorded) and `""` (explicitly empty) are **different**, so `read_image_metadata_base64` must not collapse them. Even so the matcher cannot be trusted absolutely — `loadImageWithDriverFallback()` retrying through the sweep is what makes a wrong match merely slow instead of fatal, and that retry gate reads a Python class name out of a traceback Pyodide hands JS, which nothing else pins.
- **image-corpus-measurements-need-fresh-runtimes** (2026-07-30, re-measured 2026-08-27): driver imports accumulate in a Pyodide session, so walking `chirp/tests/images/` in one runtime measures "a session where earlier files already imported things", not each image's own path — and the corpus is walked alphabetically, where `Alinco_DJ175.img` (no metadata trailer) triggers the full sweep on the very first file. Measure per-path instead, or use the cheaper oracle that avoids the question entirely: import every driver once, let CHIRP detect each image, and assert the matcher resolves either the same driver or nothing — a null resolution is correct by construction, because it takes the sweep. At this pin: **359** `.img` files, **108** with no trailer that sweep, **251** resolved on the fast path, **0** declined, all 251 agreeing with detection; **69** of the trailer-bearing images carry an `rclass` absent from the catalog, and **12** vendor/model pairs map to more than one catalog entry. Re-measuring after a submodule bump is what caught the previous figures going stale, so treat every count here as pinned to a revision rather than durable.

*Pinned by tests:*
- The matcher resolves on variant, distinguishes an empty variant from an unrecorded one, matches aliases as CHIRP does, refuses a class-name hit that contradicts the recorded identity, and returns nothing when several drivers claim one identity — `test-image-metadata.mjs`.
- A metadata-less image is undetectable until every driver is imported and loads after the sweep; a clone image whose class name also names a live-mode driver still resolves to the clone driver; the retry gate fires on a real detection failure and on nothing else; a successful fast-path match never imports every driver — `test-metadataless-image-load.mjs`.

## Repeater directories

- **rsgb-etcc-api-shape** (2026-07-31): the RSGB/ETCC beta API (`https://api-beta.rsgb.online`, self-documenting HTML at `/`) is the UK repeater directory, and unlike przemienniki.net and repeaterbook.com **it sends `Access-Control-Allow-Origin: *` on every response**, so it needs no CORS proxy — `DEFAULT_REPEATER_API_BASE` (`web/js/datasources.js`) does not apply to it. `OPTIONS` returns 405, which is harmless as long as the request stays *simple* (plain `GET`, no custom headers — adding e.g. `Accept: application/json` would force a preflight that fails). Endpoints are `/<name>/<arg>` with the arg mandatory: omitting it serves the HTML index with `Content-Type: text/html`, not JSON. `/band/<band>` (`2m`, `70cm`, … case-insensitive), `/locator/<loc>`, `/callsign/<call>`, `/keeper/<call>` and `/all/<anything>` all return `{"data":[…]}`; `/aprs/<call>` is the odd one out, returning `{"callsign","passcode"}` with no `data` wrapper. **Nothing ever returns an HTTP error**: an unknown band, locator or callsign is `200` with `{"data":null}`, so callers must null-check the payload rather than the status.
- **rsgb-locator-lookup-is-not-a-prefix-search** (2026-07-31): `/locator/` matches on **exact string equality except at 4 characters**, where it prefix-matches. So `/locator/IO92` returns all 171 records in the square (verified equal to a local `startswith` filter over `/all`), but `/locator/IO83DC` returns `null` even though `GB3OD` is stored at `IO83DC20` — only the full `IO83DC20` retrieves it. Two consequences for a "repeaters near me" flow: a 6-character query silently drops the records stored at coarser precision (of 1809 records, 464 carry only a 4-character locator, plus 1 five-character, 3 eight-character and 1 empty — so ~26% are invisible to any 6-character lookup), and 2- and 5-character queries return `null` outright. **Query the 4-character square (plus its 8 neighbours) and do the distance ranking client-side**; or just fetch `/all/systems` — the whole dataset is 555 KB raw but 73 KB gzipped in ~175 ms, which is cheaper than a 9-request fan-out and sidesteps the precision trap entirely.
- **rsgb-record-semantics** (2026-07-31): field meanings that matter when turning a record into a CHIRP channel. `tx`/`rx` are from the *repeater's* point of view and in **Hz** (integers): `tx` is what the radio listens on, `rx` what it transmits on, so the channel's frequency is `tx` and its offset is `rx - tx` (GB3KI: tx 145662500, rx 145062500 → −600 kHz). **`tx == rx` means simplex** — gateways, hotspots and packet nodes, 706 of 1809 records — and that test is more reliable than the undocumented two-letter `type` code (`AV`/`DM`/`DV` duplex; `AG`/`AP`/`DG`/`PX`/`PN` mostly simplex, with 12 `DV` and 1 `DG` exceptions). `ctcss` is Hz as a float with **`0` meaning no tone** (1006 records), `txbw` is kHz (12.5 for 1522 records, but ranges 0.05–16000 for microwave/data), `dbwErp` is dBW not watts (14 dBW = 25 W). `modeCodes` follows the flag table on `/` and can be **`null`** (2 records); DMR entries append the colour code as `M:1`…`M:15`. `status` is `OPERATIONAL` (1659), `NOT OPERATIONAL` (130), `REDUCED OUTPUT` (19) or — for one record — the empty string. `id` is the only unique key: 1809 records span 1658 distinct callsigns, because one callsign legitimately holds several ports (GB7BSK is packet on 4 m, 2 m and 70 cm).
- **rsgb-has-no-lat-lon** (2026-07-31): the payload carries no coordinates — position comes from `locator` and `extraDetails.ngr`, an OS grid reference (absent on 14 records). A 6-character locator is 2.5′ × 5′, which over the UK is a **4.64 km N-S × 5.2–6.0 km E-W** box (E-W shrinks with latitude: 5.98 km at the Lizard, 5.79 km at London, 5.22 km at Berwick, 4.53 km in Shetland — ~25 km², 7 km diagonal; the oft-quoted 9.3 km E-W is the *equatorial* value and is nearly double the truth here). Coarse for distance ranking but fine for a "nearest first" ordering; the NGR is ~100 m but is **OSGB36**, so comparing it against a WGS84 GPS fix needs a datum shift (a Helmert transform, or the ~100 m error swamps the precision it was supposed to buy). Locator → lat/lon is the standard Maidenhead decode and checks out against the data (JO01NI → 51.354 N, 1.125 E; GB3KI is at Herne Bay, 51.37 N 1.13 E). This is also what feeds the map sidecar (`web/js/row-geo.js`) on RSGB rows, and precision decides whether there is one at all: a 6-character box centre is within a few km, fine for a context map, while a 4-character centre can be 70 km out — so `buildRsgbRows` attaches coordinates only to the non-`approximate` entries and the ~26% stored at 4 characters get no map rather than a confidently wrong one.
- **coep-blocks-plain-cross-origin-images** (2026-08-17): **only `scripts/dev-server.mjs` sends `Cross-Origin-Embedder-Policy: require-corp`** (Pyodide's cross-origin isolation) — GitHub Pages cannot send those headers, so production does not serve COEP at the moment and this is a *local-development* constraint, the same one **no-crossorigin-embeds** records. Under it every plain cross-origin `<img>` is silently blocked — a repeater-map OSM tile loads fine from `curl` yet fails in the page with `ERR_BLOCKED_BY_RESPONSE.NotSameOriginAfterDefaultedToSameOriginByCoep` and shows only as a broken icon. The out: `tile.openstreetmap.org` sends `Access-Control-Allow-Origin: *`, so `img.crossOrigin = "anonymous"` turns the load into a CORS request that satisfies COEP (`web/js/ui/repeater-map.js`); it is set unconditionally, so the maps keep working whichever way the deployment headers go. Any future cross-origin asset needs either CORS mode + an ACAO header or a `Cross-Origin-Resource-Policy: cross-origin` response header on the upstream.
- **przemienniki-rxf-carries-wgs84-coordinates** (2026-08-17): each `<repeater>` in the rxf XML (from both the `/przemienniki` and `/repeaterbook` proxy endpoints, which share the format) carries `<location><latitude>/<longitude>` in decimal WGS84 plus `<locator>` and altitude fields — but not always: in a Poland 2m sample 105 of 116 repeaters had coordinates, so map features must treat them as optional per row. Rows built from these queries keep the coordinates as a `__geo` sidecar (`web/js/row-geo.js`) that header-driven serialization (TSV/CSV/upload) never sees.
- **irts-api-mostly-matches-the-shared-rxf-contract** (2026-08-27): `https://api.codeplug.org/irts` returns the same RXF XML shape and accepts the same `country`, comma-separated `band`, repeated `mode`, `onlyworking`, `latitude`, `longitude` and `range` query parameters as the existing proxy-backed directories; `/irts/meta` returns the shared JSON filter dictionary. One semantic difference matters: IRTS labels `<qrg type="rx">` as the user's receive frequency (the repeater output) and `tx` as the user's transmit frequency, while przemienniki.net labels them from the repeater's perspective. The API makes this explicit as `<perspective>radio</perspective>` versus przemienniki's `<perspective>repeater</perspective>`; parsing that field is authoritative, and a missing or unknown value must fail the query rather than guess and risk programming the two sides backwards. For EI2TRR the IRTS pair is rx 145.600 / tx 145.000, matching the official IRTS output/input table. The live directory spans both `ie` and `gb` entries (including Northern Ireland), bands `10m`, `4m`, `2m`, `70cm`, and modes `fm`, `dstar`, `dmr`, `fusion`, `nxdn`, so the UI must obtain these options from `/meta` rather than treating IRTS as Republic-of-Ireland-only or hard-coding the observed lists. IRTS is a first-party `api.codeplug.org` route and remains available through that default when a deployment leaves the configurable proxy base blank; failures surface on use instead of hiding the action.
- **rxf-perspective-governs-ctcss-not-just-qrg** (2026-09-06): the RXF `<perspective>` element labels the *whole record*, so `<ctcss type="rx">` follows the same convention as `<qrg type="rx">`. Verified against live data: przemienniki.net declares `repeater` and SR4X carries `qrg` rx 145.000 / tx 145.600 with a lone `ctcss type="rx"` of 67.0 — 145.000 is the Polish 2m *input*, so `rx` is the repeater's receive side on both elements and that lone tone is an access tone the radio must transmit. **RepeaterBook declares `radio`, not `repeater`** (only przemienniki.net is repeater-relative among the three), and IRTS declares `radio`. Across 646 live Polish records 77 are access-tone-only and 12 tone-transmit-only; the mistake is invisible on the 77 records whose two directions carry the same tone, which is why it survived (issue #103).
- **rxf-ctcss-is-not-always-a-ctcss-frequency** (2026-09-06): RepeaterBook overloads `<ctcss>` with non-tone bodies — across 1,272 live US 2m records, `CSQ` (carrier squelch, 44), `Restricted` (44) and DTCS codes such as `D023`/`D331` (35). `setRowValue` rejects these against the `rToneFreq` enum and keeps the previous value, so treating any non-empty body as a tone sets a tone *mode* with the row's default 88.5 behind it and the radio transmits a tone the directory never named. `parseCtcssFreq` (`web/js/datasources.js`) admits only a positive numeric body. Carrying the DTCS codes properly needs the `DtcsCode`/`RxDtcsCode`/`DtcsPolarity` columns and is not done.
- **a-tone-without-its-mode-is-inert** (2026-09-06): writing `rToneFreq`/`cToneFreq` does nothing on its own. `chirp_common.split_tone_encode` reads `rToneFreq` only under tmode `Tone`, reads `cToneFreq` only under `TSQL`, and reads both only under `Cross` — so any importer that sets a tone frequency must set the mode that encodes it. `applyTonePair` mirrors `chirp_common.split_tone_decode` (tx-only → `Tone`; equal pair → `TSQL`; anything else, receive-only included → `Cross` with `Tone->Tone`/`->Tone`) and each branch writes only the field its mode encodes. Gate `Cross` on the **Tone** column's options, never on `CrossMode`: `valid_cross_modes` defaults to the full `CROSS_MODES` list even when `has_cross` is false, so a populated CrossMode list is no evidence the radio can hold a split pair. 39 of 1,272 live US 2m RepeaterBook records carry a genuinely split pair.
- **setrowvalue-drops-out-of-band-writes-silently** (2026-09-05): `setRowValue` is a *validating* writer, not an assignment. `normalizeValue` (`web/js/ui/channel-values.js`) returns the column's **previous** value when a `freq` write falls outside the driver's `valid_bands`, and it returns no signal that it did — so a row builder that does not re-read the cell cannot tell a rejected write from an accepted one. `Offset` is deliberately exempt from the band check (`shouldCheckBands = column !== "Offset"`), and that asymmetry is what makes the failure look plausible instead of empty: a 70cm repeater written to a 2m-only radio keeps its `-7.600000` shift while the Frequency stays blank. A blank Frequency is not inert downstream — `_apply_rows_to_radio_instance` reads it as "erase this memory" on upload — so **every** builder that writes a frequency must re-read `row.Frequency` and drop the row when it did not take (issue #101). Both builders now do: `buildRsgbRows` (`web/js/rsgb.js`) and `buildPrzemiennikiRows` (`web/js/datasources.js`, serving przemienniki.net, RepeaterBook and IRTS) return `{ rows, skipped }` with a per-record reason of `"frequency"` or `"mode"`, and `repeater-sources.js` phrases both the same way for every source.
- **rxf-absent-qrg-parsed-as-zero-not-nan** (2026-09-06): `Number("")` is **0, not NaN**, so reading an RXF `<qrg>` with a bare `Number(firstText(...))` turned an *absent* frequency into a finite 0 MHz that satisfied every `Number.isFinite` guard downstream — which made the receive/transmit fallbacks in `buildPrzemiennikiRows` unreachable for exactly the case they exist to handle (they stayed live only for a *non-numeric* body, where `Number("abc")` is NaN). A repeater-perspective entry carrying only `<qrg type="tx">145.6</qrg>` therefore imported as Duplex `-` with a 145.600000 offset; radio-perspective lost the row to the band check (issue #102). `parseQrgMhz` (`web/js/datasources.js`) now returns NaN for anything absent, empty, non-numeric **or `<= 0`** — a literal `0` in the feed is as meaningless as a missing element, and only the `> 0` test catches it, since `latitude`/`longitude`'s `|| NaN` idiom still coerces the string `"0"` to a finite 0. **This parser is not przemienniki-specific**: `remoteDirectorySource` routes przemienniki.net, RepeaterBook *and* IRTS through the same `parsePrzemiennikiXml`, so any RXF parsing change lands on all three. Empirically the proxy never omits a `qrg` — 7,960 live records (przemienniki PL/DE/CZ/GB, RepeaterBook PL/US/CA, IRTS all/IE) had **zero** missing, empty or zero frequencies — so this was latent robustness rather than a bug users were hitting, and the feeds are the only input path (there is no user-supplied RXF import).
- **rsgb-contract-tests-are-opt-in** (2026-07-31): the four findings above are pinned by `scripts/test-rsgb-live.mjs` (`npm run test:api`), which is deliberately **not** in `npm test` because it needs the network and a third party's uptime — the ordinary RSGB unit tests run on transcribed fixtures and stay green if the upstream changes shape underneath us. Two of its assertions are staleness alarms on curated lists rather than API checks: **every offered band still holds a repeater** and **no omitted band has gained one** (4m, 13cm, 6cm, 24GHz and SHF were excluded on a snapshot of a live directory, so a newly coordinated 4m repeater silently stops being filterable).

*Pinned by tests:*
- One modal serves every directory (`web/js/ui/repeater-query.js` + `repeater-sources.js`): the form is rebuilt from field components on each open, which is the reset policy — filters return to per-source defaults while the position persists across opens and source switches; RSGB stays available with a blank proxy base and its square fan-out stays a bare GET (a header would trigger the CORS preflight the API 405s) — `test-ui-repeater-modal.mjs`.
- The field components behave identically for every source — locator↔coordinate two-way sync, blank numeric fields reading NaN rather than 0, checkbox-group defaults — `test-ui-query-fields.mjs`.
- No import writes a row the selected radio cannot hold: an out-of-band frequency or an unusable mode is skipped and counted rather than inserted blank, for RSGB and for the RXF directories alike — `test-datasources.mjs`, `test-rsgb.mjs`, `test-ui-repeater-modal.mjs`.
- An RXF entry carrying only one of its two `qrg` elements imports as simplex on the frequency it does have, rather than as a split against a phantom 0 MHz; an entry with neither is skipped — `test-datasources.mjs`, `test-ui-repeater-modal.mjs`.

## WebUSB serial adapters

- **webusb-test-endpoints-must-name-their-type** (2026-08-17): WebUSB's `USBEndpoint` descriptors always identify their transfer `type`, but the original FTDI unit-test fake omitted it because that driver selected endpoints by direction alone. Once FTDI correctly filters for `type === "bulk"`, an untyped fake rejects every otherwise-valid `open()`. Driver fixtures must model descriptor type explicitly; the FTDI regression test also places an interrupt IN endpoint after bulk IN so the old direction-only selection demonstrably chooses the wrong pipe.
- **ch340-version-not-bcddevice** (2026-07-28): the CH340/CH341 protocol branches on the chip version returned by vendor request `0x5F`, **not** on the USB `bcdDevice` word — an 0x1a86:0x7523 cable reporting `bcdDevice 0xc233` still reports a version of 0x30/0x31 over the wire. Version > 0x27 sets bit 7 of the prescaler value (otherwise the chip withholds data until a full 32-byte packet, which stalls short CHIRP replies); version >= 0x30 configures framing through the LCR register pair, and older parts are left at their 8N1 defaults.
- **webusb-vendor-filters-are-too-broad-for-wch** (2026-07-28): FTDI and Prolific can be filtered by vendor id alone, but WCH's 0x1a86 also covers CH9102/CH343 parts that enumerate as CDC-ACM (and non-serial chips). The CH340 chooser filters on exact vendor/product pairs so those devices fall through to the CDC polyfill instead of getting the CH340 register map.

- **loopback-cannot-verify-baud** (2026-08-15): a TX-to-RX jumper proves nothing about baud rate. Both directions clock off the same divisor, so a wrong `ch340GetDivisor()`/`ftdiConvertBaudrate()` result echoes back perfectly — divisor math is only checkable against published encodings (the unit tests) or against a *second* adapter cross-wired at a known rate. What loopback does cover is everything between the driver and the wire: packet-boundary framing, byte transparency (0x11/0x13 survive only if no software flow control is on), idle handling, read timeouts and reopen. `web/js/loopback-suite.js` is transport-agnostic — it runs against any Web Serial-shaped port, which means the same cases cover native `navigator.serial`, all four WebUSB chip drivers and the CDC polyfill.
- **chip-ports-were-not-reopenable** (2026-08-15): `close()` in all three WebUSB drivers latched `_closed = true`, and `open()` never cleared it — so a reopened port object rebuilt its streams around a `pull` whose `while (!isClosed())` was false on entry. Per the Streams spec a `pull` that resolves without enqueuing is never re-invoked, so the port handed back readable/writable that silently delivered nothing, with no error anywhere. It never bit a user at the time because `createWebUsbSerial().requestPort()` constructs a fresh port object per connect and `BrowserSerialBridge` drops its reference on close — the app then had no path that reopened one. It bit the loopback suite immediately, which is the argument for having a test that reopens. **Since 2026-09-05 the app does reopen ports** (see **baud-rate-is-latched-at-open**), so this is now a live path rather than a suite-only one.
- **webusb-chip-ports-have-no-getsignals** (2026-08-15, revised 2026-08-19): the FTDI, PL2303 and CH340 drivers implement `setSignals` (needed by `prepareClone`) but not `getSignals`, while native Web Serial ports have both. So input control lines — CTS, DSR, DCD — are unreadable on those three, and anything that wants to *observe* a radio asserting a line works only on desktop Chrome. The loopback suite's control-line case skips itself on ports without `getSignals` rather than failing a correctly jumpered adapter. **CP2102 is the exception**: `GET_MDMSTS` (0x08) answers with a single byte carrying CTS/DSR/RI/DCD alongside the two output lines, so that driver implements `getSignals` and the control-line case actually runs on it. Nothing in the app calls it — it exists for the loopback page, which is the only place an input line is observed.
- **one-bulk-in-transfer-at-a-time-drops-bytes** (2026-08-17): a WebUSB read path that issues the next `transferIn` only after the previous one resolves leaves the endpoint unqueued for the whole round trip, and the chip's RX FIFO overruns in that gap — silently, with `status: "ok"` throughout and no error at any layer. Measured on a Pixel 10 (Chrome 151) against a CH340G: at 115200 a single outstanding transfer lost bytes on **every** 16 KB echo and on ~1–6% of bytes generally, while 9600 and 57600 never lost one. The chip's 32-byte bulk IN endpoint is the reason it bites CH340 first — it needs a completed transfer every 2.8 ms at 115200, where FTDI and PL2303's 64-byte endpoints get twice the slack. Linux has always done this correctly and `ch341.c` is where to read it: it sets no `bulk_in_size` and no custom read callback, so it inherits `read_urbs[2]` (`include/linux/usb/serial.h`) — two URBs submitted at open by `usb_serial_generic_submit_read_urbs()`, each resubmitted from its own completion callback, so the endpoint is never idle. Depth 2 suffices in a kernel resubmitting in interrupt context; a JS resubmit crosses Chrome's IPC boundary and the event loop, which is why `READ_PIPELINE_DEPTH` is 16 **and** the stream carries a matching `highWaterMark` — a default queue of 1 puts the consumer's own work back on the critical path and cost a dropped packet mid-suite even at depth 8. Confirmed on a PL2303HX too (2026-08-17): its 64-byte endpoint gives twice the slack, so the 256-byte cases pass and only the suite's 16 KB echo at 115200 fails — 3 of 10 runs before the fix, 0 of 12 after. The margin is what differs, not the defect. And confirmed on an FT232R (2026-08-17), which closes the set — all three drivers had it. Its margin is the widest of the three: the same 64-byte endpoint as the PL2303, plus a 4 ms latency timer that makes the chip *deliberately* hoard bytes while the host is not polling, plus (per the datasheet) a 256-byte receive buffer, so at 115200 it can absorb ~22 ms of wire time before anything is lost. It still loses bytes — 2 of 30 suite runs before the fix, both the 16 KB echo at 115200 (75 and 13 bytes short of 16384, `status: "ok"` throughout), against 0 of 60 after. Note what that rate means for evidence: at ~7% per run a clean run proves nothing, and no run count anyone will sit through separates 7% from 0% at any conventional confidence — the case rests on the reproduction plus the structural argument, not on the after-numbers alone. Note also the isolated benchmark is *less* sensitive than the suite: a bare pump over the raw stream showed no PL2303 loss at all, because the suite's per-chunk buffering is itself part of what starves the endpoint.
- **ch340-strands-exact-multiple-replies-on-multi-packet-reads** (2026-08-17): the obvious cure for the above — ask for more bytes per `transferIn` — is wrong for this chip, and badly so. A bulk IN transfer ends on a short packet or on the full requested length, and the CH340 sends nothing to terminate one, so against a 512-byte request a 32-, 64- or 96-byte reply **never arrives at all** (measured: 0 bytes delivered, the transfer simply stays pending). Any reply whose length is an exact multiple of the 32-byte packet size strands, which is precisely the shape of a fixed-size CHIRP clone block. Linux avoids this by leaving `bulk_in_size` unset so the core allocates exactly `wMaxPacketSize`. Throughput must come from queue depth; the request length stays at one packet, and `test-ch340-webusb.mjs` pins it. This one is chip-specific: a PL2303HX given a 1024-byte request returned 128-, 192- and 1024-byte replies (all exact multiples of its 64-byte packet) promptly, so it does terminate multi-packet transfers. The one-packet rule is applied there anyway — there is nothing to gain from a longer request once the queue is deep, and the failure mode if a chip does not terminate is a permanent silent hang.
- **driving-the-loopback-page-on-a-phone** (2026-08-17): these chip defects only appear on a phone, and no hardware CI can catch them, so the measurement rig is worth writing down. Wireless adb frees the USB port for the adapter: `adb pair <host>:<pairingPort> <code>` then `adb connect <host>:<connectPort>` (both ports come from `adb mdns services`, and they differ — the pairing service only advertises while the phone's pairing dialog is open). `adb reverse tcp:8000 tcp:8000` points the phone at `npm run dev` on the laptop, and **`http://localhost:8000` is a secure context on Android**, so WebUSB works without HTTPS or a tunnel — which is what lets a driver be edited and reloaded against the real adapter instead of testing whatever is deployed. `adb forward tcp:9222 localabstract:chrome_devtools_remote` then drives the page over CDP: `Target.createTarget` to open a tab, `Runtime.evaluate` with `userGesture: true` to satisfy `navigator.usb.requestDevice()`'s activation requirement, and thereafter `import()` the driver and `runLoopbackSuite` directly, looping the whole suite N times in one evaluate. A run is ~21 s, so a 30-run comparison is ~10 minutes unattended. Chrome for Android has no `/json/new`, hence `Target.createTarget` over the browser WebSocket.
- **cp210x-requests-are-interface-addressed** (2026-08-19): the CP210x family is the odd one out among the four drivers. FTDI, PL2303 and CH340 take their vendor requests with a *device* recipient; every CP210x UART request (`IFC_ENABLE`, `SET_BAUDRATE`, `SET_LINE_CTL`, `SET_MHS`, `GET_MDMSTS`, `SET_FLOW`, `PURGE`) is `bmRequestType 0x41/0xc1` — vendor, **interface** recipient — with `wIndex` carrying the interface number. WebUSB validates that pairing: an interface-recipient transfer only goes through on a claimed interface whose number matches `index`. The one exception is `VENDOR_SPECIFIC` (0xFF, used here to read the part number), which is device-recipient yet *still* puts the interface number in `wIndex` — see `cp210x_read_vendor_block()`. Hardcoding zero works on a single-UART CP2102 and silently addresses the wrong port on a CP2105/CP2108, so the number comes from the descriptor; `test-cp2102-webusb.mjs` opens against interface 1 to pin it.
- **cp210x-vendor-wide-filter-needs-a-dispatch-guard** (2026-08-19): the filter breadth and the dispatch predicate are separate decisions, and this family needs them to differ. The *chooser* filters on Silicon Labs' 0x10c4 vendor-wide, because ~150 of the kernel `id_table`'s entries are OEM cables carrying a CP210x under a custom product id — an exact-pair allowlist (the call made for WCH in **webusb-vendor-filters-are-too-broad-for-wch**) would leave those cables invisible in the chooser, and a device that never appears produces no diagnostic at all. But the vendor id alone does not mean "single-UART bridge speaking the vendor protocol": 0x10c4 also covers the dual/quad-UART CP2105/CP2108, the HID-based CP2110/CP2112, the SPI CP2130, and — the one the product id cannot catch — the **CP2102C**, which carries the same ids as its siblings yet enumerates as standard USB CDC-ACM and belongs to the polyfill. So `isCp2102Device()` rejects the known non-single-UART products by id *and* declines anything whose descriptors declare a CDC interface class, before any configuration write is issued. The descriptors are readable before `open()`, which is what makes the CDC check possible at dispatch time.
- **webusb-bulk-out-failures-do-not-reject** (2026-08-19): `transferOut()` resolves with a `USBOutTransferResult` — `{status, bytesWritten}` — rather than rejecting, exactly like `transferIn()`. A write path built as `await device.transferOut(ep, chunk)` therefore reports success on a stalled transfer *and* on a short one, so a lost protocol block surfaces as a mysteriously wrong clone rather than a failed upload. The CP2102 driver checks the status, clears a halted OUT endpoint before failing, and resumes a short write from `bytesWritten`. **The FTDI, PL2303 and CH340 drivers still have the unchecked form** — not yet fixed there because all three are hardware-verified as they stand and the change belongs in its own pass.
- **cp210x-event-mode-is-not-cleared-by-enabling** (2026-08-19): the natural assumption — that `IFC_ENABLE(UART_ENABLE)` starts the chip from a clean slate — is wrong, and wrong in a way that corrupts data rather than failing. Per AN571, event-insertion mode is cleared by a USB reset or by `IFC_ENABLE(UART_DISABLE)`; *enabling* the interface leaves it exactly as it was. A driver that inherits an event mode some earlier session turned on gets a bulk IN stream where 0xEC is an escape prefix and line/modem status is spliced inline, which reads as plausible clone data. The driver therefore disables the interface before enabling it, an extra control transfer that costs one round trip at open and is pinned by `test-cp2102-webusb.mjs`. Nothing in this app ever enables event mode, so the exposure is entirely to what another host driver left behind.
- **cp210x-flow-block-transforms-bytes-too** (2026-08-19): the `SET_FLOW` block's `ulFlowReplace` word does not only carry flow control. Bits 2-4 make the chip *rewrite the received byte stream*: substitute a character on a parity/framing error, **discard every received NUL**, substitute a character on a break. NUL stripping alone silently shortens a binary clone image, and none of the three fails loudly. They are cleared alongside the XON/XOFF and RTS bits, and the test seeds a chip reporting all of them on.
- **cp2102n-errata-e104-and-e106** (2026-08-19): two A01 errata shape the driver in ways nothing in the protocol docs would suggest. **E104**: the firmware reads the first byte of `ulXonLimit` as `ulFlowReplace`, so a perfectly ordinary FIFO threshold of `0x80` there selects RTS flow control — TX gets gated and `SET_MHS` can fail while the real flow word looks innocent. Both thresholds are therefore written as zero, never preserved from `GET_FLOW`; they are unused with software flow control off. **E106**: disabling the UART does not reset the DTR/RTS outputs, so the host has to drive them low itself. Without that, closing the port can leave a line asserted into a radio until the cable is unplugged — for a programming cable, holding the radio in clone mode. `close()` writes both lines low before `PURGE` and the UART disable.
- **cp210x-holds-flow-control-in-a-block-nothing-resets** (2026-08-19): `IFC_ENABLE` re-enables the UART, but it does *not* touch the 16-byte `SET_FLOW`/`GET_FLOW` block that holds hardware handshaking (CTS/DSR/DCD), the DTR/RTS modes and the `AUTO_TRANSMIT`/`AUTO_RECEIVE` XON/XOFF bits. Whatever the last driver to touch the chip left there is what a fresh session inherits, and two of those settings corrupt a clone silently rather than failing it: XON/XOFF eats 0x11 and 0x13 out of the image, and CTS handshaking lets a radio's control line gate our transmit. So the driver writes the block at every open — read-modify-write like the kernel, so the chip's own Xon/Xoff FIFO thresholds and reserved bits survive, falling back to a constructed block if the chip will not answer `GET_FLOW`. Not observed in the wild (a factory-default part has all of it off); it is one control transfer against a failure mode with no error message.
- **baud-rate-is-latched-at-open** (2026-09-05): a port's line rate is fixed by `port.open({baudRate})` and there is no Web Serial call that changes it in place — no `setBaudRate`, and `getInfo()` does not even report the current rate. The only way to re-rate is `close()` then `open()`, and the non-obvious part is that this costs **no user gesture and no second chooser**: the browser's permission is granted to the `SerialPort` object, not to the `open()` call, so reopening the handle already held is silent. (node-serialport is the odd one out — it has `port.update({baudRate})`, which re-rates without closing; `scripts/test-radio-harness.mjs` uses it.) This matters because CHIRP declares `BAUD_RATE` per driver, spanning 9600–115200 across the catalog, while the app opens the port once at Connect from whatever radio was selected *then*. Switching the dropdown afterwards used to leave the clone running at the old rate, failing as timeouts or garbage with nothing naming the cause (issue #76). The rate is therefore re-applied from the driver on every clone in `prepareClone`, before the control lines and settle delay, rather than trusted from connect time. Two consequences worth keeping in mind: a reopen swaps the reader, so any read loop must be pinned to the reader it started with or it will consume from its successor's stream; and a reopen that fails leaves a port that is open at neither rate, which has to be torn down rather than reported as connected.
- **webusb-chip-ports-are-8n1-only** (2026-09-05): the sibling of **webusb-chip-ports-have-no-getsignals**, and the one that corrupts data rather than merely hiding it. All four WebUSB drivers accept `open()`'s `dataBits`/`stopBits`/`parity` and read none of them: FTDI issues `SIO_SET_DATA` as `DATA_8N1` (`ftdi-webusb.js:194`), PL2303 writes the line-coding block with the three framing bytes hardcoded (`pl2303-webusb.js:268-271`), CH340 writes `LCR_8N1` and leaves pre-0x30 parts at their power-on 8N1 (`ch340-webusb.js:242-248`), and CP210x issues `SET_LINE_CTL` as `LINE_CTL_8N1` (`cp2102-webusb.js:510-511`). Baud rate *is* honoured by all four, so a rate reopen works everywhere and only the frame does not. That asymmetry is the trap: a reopen carrying `parity: "even"` succeeds at every layer and comes back wrong on the wire, where every byte is then misframed and the clone fails on garbage naming nothing. So each port declares `supportsFraming = false` and `reconfigure()` refuses a framing change on those transports instead of reporting a success the wire does not have — absence of the flag means the port honours `open()`'s framing, which covers native Web Serial and the CDC polyfill. The radios this actually gates are the handful in **framing-is-set-after-open-but-never-mid-clone**; on desktop Chrome's native ports they work, on a WebUSB adapter they now fail with a message that says why. Teaching the four drivers real framing is a chip-by-chip encoding job (FTDI's `SIO_SET_DATA` bits, PL2303's coding bytes, CH340's LCR pair, CP210x's `LINE_CTL` word) that cannot be verified without the hardware, which is why the declaration came first.
- **cp210x-quantises-baud-host-side** (2026-08-19): `SET_BAUDRATE` (0x1E) takes a plain u32 little-endian rate, not a divisor — but the chip silently maps it to a rate it can actually generate, and AN205 says the result of asking for more than 1053257 baud is *undefined*. The kernel quantises host-side first (AN205 Table 1 for CP2101/2/3, `div = round(48e6 / (2 × prescale × request))` from the CP2104 on, prescale 4 below 365 baud) and this driver ports that, so the rate it reports is the rate on the wire. Every rate CHIRP uses — 9600, 19200, 38400, 57600, 115200 — is an exact table entry, so the quantiser is a no-op on the radio path; it earns its place by clamping, and `test-cp2102-webusb.mjs` pins the standard rates against a quantiser that ever starts shifting them.


*Pinned by tests:*
- The kernel's `CH341_QUIRK_LIMITED_PRESCALER` is inert here — it only changes the encoded divisor when the first-pass divisor comes out odd, and every baud CHIRP uses yields an even one — `test-ch340-webusb.mjs`.
- Each chip family's init sequence, the version branch, and the stalled-endpoint recovery on the read path — `test-ch340-webusb.mjs`, `test-ftdi-webusb.mjs`, `test-pl2303-webusb.mjs`, `test-cp2102-webusb.mjs`. `test-webusb-serial.mjs` keeps only what is not driver behaviour: the FTDI divisor math, the status-header helper and the chooser's vendor dispatch.
- Every WebUSB chip driver declares that it cannot change framing, and a framing change on one is refused rather than reopened, while a baud-rate change on the same port still goes through — `test-serial-reconfigure.mjs`.
- A clone re-rates the port it already holds to the selected driver's `BAUD_RATE` — reopening the same handle without a second `requestPort()`, leaving an already-correct rate untouched, keeping the connected rate when a driver declares none, and tearing the session down when the reopen fails — `test-clone-baud-rate.mjs`, with the Python-to-bridge hand-off in `test-clone-baud-plumbing.mjs`.
- A disconnect event for the open port closes it and reports the loss once, one for any other device leaves it alone, and a normal close takes the watch down with it — `test-port-loss.mjs`, with the clone buttons' side of it in `test-clone-button-gating.mjs`.
- All four chip read paths keep a full pipeline of bulk IN transfers queued, carry the matching high-water mark, retire the pre-stall queue before clearing a halt, and ask for exactly one packet per transfer — `test-ch340-webusb.mjs`, `test-pl2303-webusb.mjs`, `test-ftdi-webusb.mjs`, `test-cp2102-webusb.mjs`. Each assertion is checked against the defect it claims to catch: shrinking the depth, dropping the queuing strategy, keeping the queue across `clearHalt` and lengthening the request each fail their own test and no others.
- The CP2102 defences that only bite on inherited or faulty state, each against the failure it claims to prevent — the disable-before-enable that clears an inherited event mode, the flow block's byte-transform bits and zeroed XON/XOFF limits, both control lines driven low at close, a stalled or short bulk OUT surfacing as a failed write, and a failed open handing the device back so the retry is not poisoned — `test-cp2102-webusb.mjs`.
- Every driver's read/write path end to end, with no hardware: `test-loopback-harness.mjs` fakes a USBDevice whose bulk OUT feeds its bulk IN (FTDI status header and all), and `test-loopback-suite.mjs` runs the real suite over it. The fault injectors exist so each case is shown to *fail* on the defect it claims to catch — truncated writes, doubled echoes, swallowed XON/XOFF, a link that dies after one idle gap, an FTDI device sending no status header — because a loopback case that cannot fail is worse than no case at all.

## Hosting & deployment

- **pages-deploy-and-cache-window** (2026-07-22, trimmed 2026-08-07): Pages deploys via `.github/workflows/pages.yml` from `dist/`, HTTPS enforced (Web Serial/WebUSB require a secure context). **The live host is `https://codeplug.org/`**, named in `./CNAME` — which `scripts/retain-deployed-assets.mjs` reads rather than taking a hostname argument, because the two drifted silently for a week once. GitHub Pages serves everything with a fixed, non-configurable `Cache-Control: max-age=600` + ETag (Fastly), creating a ≤10-minute post-deploy window where a stale `index.html` can 404 on old content-hashed asset names; the mitigation is to fetch the deployed `asset-manifest.json` and carry the previous generation of hashed assets into the new artifact, chained via `retained-assets.json` with a 7-day max age. Heavy payloads (Pyodide, CHIRP sources) come from jsDelivr with long cache lifetimes, not Pages.
- **build-dist-rewrites-are-textual** (2026-08-03, widened 2026-08-07): `scripts/build-dist.mjs` hashes `.js/.css/.py` and rewrites references with a plain `split`/`join` over the whole file, only inside `REWRITE_EXTS` (`.html/.js/.css`). Both halves bite. Writing an asset path in an HTML or JS **comment** rewrites that too — a comment reading "see web/js/analytics.js" ships as "see web/js/analytics.c6e8292118.js", so refer to modules by name in prose, not by path. And a file outside `REWRITE_EXTS` is copied verbatim: `manifest.webmanifest` is never rewritten, so anything it points at must be an unhashed path or it will 404 in `dist/` — which is why the icons live in `web/images/`. And `.mjs` is in **neither** set: the shared logic modules (`call-queue.mjs`, `python-sources.mjs`, `image-metadata.mjs`, `runtime-bootstrap.mjs`) ship unhashed and unrewritten, so they get no cache-busting on a host where **pages-deploy-and-cache-window** says the headers cannot be set — verified 2026-09-06, when a `build:dist` emitted `runtime-rpc.<hash>.js` next to a bare `runtime-bootstrap.mjs`. Harmless only because every `.mjs` here is a leaf that imports nothing; the day one imports a hashed `.js` it will 404 in `dist/`, so keep them import-free or add the extension to both sets.

*Pinned by tests:*
- Asset retention takes its host from `CNAME`, fails the build on a host serving nothing, and still exits 0 on a real first deploy — `test-retain-assets.mjs`.
- Every file the manifest and the install flow need survives into `dist/`, and each icon's real IHDR size matches its declared `sizes` — `test-web-manifest.mjs`, `REQUIRED_WEB_FILES` in `build-dist.mjs`.

## PWA / install

- **pwa-install-needs-no-service-worker** (2026-08-02): Chrome dropped the service-worker requirement for installation in **108 on Android** (112 on desktop) — `web/manifest.webmanifest` plus a 192 and a 512 icon is enough for Chrome on Android to mint a WebAPK (standalone window, launcher icon, own task in the app switcher). The old criteria caused sites to bolt on empty `fetch` handlers purely to pass the check, which is why the requirement went away; do not add a pass-through service worker here to "make it installable". A worker is still the way to get *deterministic* caching — a WebAPK's storage is Chrome's ordinary evictable HTTP cache, so a returning user can silently re-download the whole Pyodide payload — but that is real offline work (Pyodide + the CHIRP wheel + `web-serial-polyfill`, all cross-origin from jsDelivr), and it has to coordinate with the hashed-asset scheme `scripts/retain-deployed-assets.mjs` already manages. Startup itself is cheap and does **not** pull driver sources: `loadRadioCatalogFromStatic()` reads the 84 KB `web/radio-catalog.json` and Pyodide never boots (see **static-driver-catalog**).
- **webapk-start-url-changes-take-days** (2026-08-05): editing `start_url` does not reach installed apps for a day or more — Chrome re-reads the manifest roughly daily and only then queues Play Services to re-mint the WebAPK. Until that lands, an installed app launches the old URL and its hits carry the old `dl`, so a freshly deployed analytics marker looks broken when it is merely not propagated. Check `location.href` in the running app before debugging anything else; a fresh install picks the new value up immediately and is the fastest way to confirm the manifest itself is right.

## Analytics

- **analytics-has-to-be-gated-at-the-tag** (2026-08-07): every copy of this app ships the same measurement ID, so a dev server, a fork's Pages site and the production deployment all report into one property unless something stops them — and one developer reloading localhost all day is then indistinguishable from real traffic, which is fatal to any per-driver success rate. Gating only *our* `trackEvent` calls is not enough: the vendor tag sends `page_view` and `session_start` by itself, which is the bulk of it. `web/js/analytics.js` therefore injects the `googletagmanager.com/gtag/js` loader itself, past a `location.hostname` check against `ANALYTICS_HOSTS` (the apex plus `www`, because `CNAME` points at the apex and an unredirected `www` visitor is real traffic); neither page carries a loader tag, so off-domain nothing is requested from the vendor at all. Two consequences worth knowing: the parse-time head start of a static `<script async>` is gone (the `preconnect` went with it, being useless once the request is issued from the module), and analytics can no longer be observed on localhost — a change to it is only verifiable in unit tests or on production. Also: `trackEvent` swallows a throwing `gtag`, because content blockers commonly replace it with a stub that throws, and telemetry must never be able to fail a clone.
- **pwa-traffic-needs-a-marker-on-every-hit** (2026-08-03, merged with the `gtag("set")` finding 2026-08-05): a WebAPK launch sends no `Referer` and navigates to the same origin, so in GA it is indistinguishable from a direct browser visit. Two independent markers cover it: `start_url` carries `?utm_source=pwa&utm_medium=homescreen` (session-scoped attribution, which is why the manifest's explicit `"id": "/"` matters — without it, changing `start_url` would make Chrome treat this as a different app and orphan existing installs), and a `display_mode` parameter rides on every hit for the navigations that leave `start_url` behind. **That parameter must not be set with `gtag("set", …)`** — it reads like a global for every later hit, but GA4 never attaches custom parameters from it, so the value silently never reaches the payload. It has to ride on the `config` call (which the automatic `page_view` inherits) or be passed per-event; `trackEvent()` stamps it on every event itself. Installs are only observable through `beforeinstallprompt`/`appinstalled`, because the browser mints the WebAPK without navigating anywhere measurable — and never `preventDefault()` the prompt event to measure it, which suppresses Chrome's own install UI. Verified the only way this is verifiable: `performance.getEntriesByType("resource").filter(r => /google-analytics/.test(r.name)).map(r => r.name)` in a page inspected over `chrome://inspect`, reading the collect URL's `ep.*` params. A unit test cannot catch this class of bug — it can only pin the call shape — and note GA sends custom params regardless of registration, so absence from the payload always means "never attached", never "not registered yet". Headless Chromium ignores `Emulation.setEmulatedMedia` for `display-mode`, so that detection is only checkable in unit tests, never in a screenshot run.
- **ga-custom-dimensions-are-syncable** (2026-08-04): GA4 custom dimensions are a first-class Admin API resource (`analyticsadmin.googleapis.com/v1beta/properties/{id}/customDimensions`, methods create/list/get/patch/**archive**), so the console is not the only way to register them — `npm run ga:dimensions` diffs the property against `CUSTOM_DIMENSIONS` in `web/js/analytics.js` and `-- --apply` closes the gap. Four things shape the script: `parameterName` and `scope` are **immutable**, so renaming either is a new dimension with empty history and the plan reports it as a conflict rather than patching; there is **no delete**, only archive, which is what frees a slot; registration is **never retroactive**, so a parameter left undeclared collects nothing until someone notices; and property access is granted in GA Admin > Property access management (Editor), **not** through Cloud IAM — a service account with project-owner still gets 403. Auth is a hand-rolled JWT-bearer exchange (`node:crypto` + `fetch`) rather than `@google-analytics/admin`, which pulls gRPC in for four REST calls. The measurement id is not a property id; the script resolves one to the other via `accountSummaries` → `dataStreams[].webStreamData.measurementId`, which needs account-level visibility and is why `--property` exists. A fifth constraint is undocumented and only surfaces at `--apply` time: `displayName` may contain **only letters, digits, underscores and spaces**, so a name as ordinary as "Duration (ms)" fails the create with a 400 — and because creates are applied one at a time with no rollback, a bad name would abort mid-run and leave the property half-synced, which is why the charset is enforced locally before any call is made.
- **ga-event-scoped-slots-are-nearly-spent** (2026-08-07): `CUSTOM_DIMENSIONS` declares **36** parameters, all `EVENT`-scoped, against GA4's limit of 50 (`SCOPE_LIMITS`, `scripts/ga-dimensions.mjs:37`). Combined with the three constraints above — immutable names, archive-not-delete, never retroactive — a new parameter is a scarce and effectively one-way resource. That is why the event-coverage work added *dimensions to existing events* rather than minting new events: a dimension on an event that already fires shares its denominator and costs one slot, where a new event costs a slot per parameter it introduces.
- **encoding-declaration-has-1024-bytes** (2026-08-07): HTML requires `<meta charset>` inside the first 1024 bytes, and an analytics comment block above it is enough to push it out — it went from byte 338 to byte 1607 once, and em dashes in that comment put non-ASCII *before* the declaration. Harmless while the server sends `charset=utf-8` (GitHub Pages does), mojibake over `file://` or a bare dev server. `<meta charset>` is now the first line of `<head>` on both pages so prose above it can grow freely.

*Pinned by tests:*
- Off the production host nothing at all happens — no vendor request, no `gtag`; on it the loader is requested exactly once; the launch context rides on `config` and never on a bare `set()`; the install prompt is measured without suppressing the browser's own; `<meta charset>` stays inside the first 1024 bytes — `test-analytics.mjs`.
- Error text is mapped onto a fixed vocabulary rather than sent verbatim, driver identity carries nothing else, and every parameter the helpers produce is a declared dimension — `test-analytics-events.mjs`, `test-ga-dimensions.mjs`.

## Error reporting (Sentry)

- **sentry-needs-the-same-host-gate-as-analytics** (2026-09-06): the first attempt was the vendor's loader script as a static `<script>` in the page head, and it was reverted within minutes for the reason spelled out in **analytics-has-to-be-gated-at-the-tag** — every copy of this app carries the same DSN, so a dev server and every fork's Pages site report into one project, and an error from someone's half-finished branch is worse than no error at all because it reads as a bug report against code that was never deployed. `web/js/sentry.js` mirrors the analytics module instead: a `location.hostname` check against `SENTRY_HOSTS` first, then a **dynamic** `import()` of the SDK. The import has to be dynamic — a static one is fetched at parse time, before any gate can run, which is exactly what the static tag did wrong. A DSN is not a secret (it only grants the right to submit events), so shipping it in a public file is fine; the gate, not secrecy, is what keeps other people's copies out.
- **sentry-tracing-is-not-a-call-graph, and profiling cannot work here** (2026-09-06): the two are different products and only one of them was ever plausible on this host. *Tracing* (`tracesSampleRate`) records spans the SDK instruments — page load, resource fetches, XHR/fetch, user-interaction timings — so it answers "what took how long", never "which function called which". *Profiling* (`browserProfilingIntegration`) is the one that yields real sampled call stacks, and it is built on the JS Self-Profiling API, which the browser only exposes when the document is served with a `Document-Policy: js-profiling` **HTTP header**. There is no `<meta>` equivalent for that header, and per **pages-deploy-and-cache-window** GitHub Pages serves a fixed, non-configurable header set — so browser profiling is unavailable here at any effort short of moving off Pages to a host with header control. What does survive is the part that answers the question in practice: the JS **stack trace** on every captured error is the call chain at the moment of failure, and it is readable as-is because `build-dist.mjs` hashes and rewrites filenames but never minifies, so no source maps are needed or uploaded. Python frames are not JS frames — a CHIRP failure arrives as traceback *text* in the message body, so it is never a clickable Sentry stack, only redacted prose.
- **a-crash-report-needs-a-signal-not-a-proxy** (2026-09-06): `onRuntimeCrash` used to fire on `!bootstrapFailed && !pyodide` — reading "the pyodide handle is unset" as "the bootstrap failed", when it actually means "the bootstrap has not assigned yet". That proxy was wrong in **both** directions, and each direction hurt a different consumer. The driver-index fetch in `listDriverModules()` is plain HTTP to `data.jsdelivr.com` and runs *before* `ensurePyodide()` in `loadRadioCatalogFromSources()`, so a blocked CDN with no `radio-catalog.json` reported a network error as RUNTIME CRASH and filed a false `error_kind: "runtime_crash"` in Sentry; conversely `ensurePyodide()` assigned `pyodide` from `loadPyodide()` *before* `seedPyodideRuntime()`, so the genuinely reportable failure — the interpreter loaded but the runtime bridge never seeded — left the handle truthy and was never reported at all. The two compounded, and the first attempt to fix that compounding was itself wrong in a way worth keeping: a boolean latch cleared on a successful bootstrap **cannot re-arm**, because `ensure()` caches the runtime once it succeeds, so a success is never followed by another failure and the clear is unreachable in every case that would matter — a first `loadPyodide` failure still permanently silenced a distinct `seedPyodideRuntime` failure on the retry (caught in review of PR #139). Deduplication has to key on the failure, not on a latch: every call queued behind one attempt rejects with the **same error object**, so error identity is exactly the attempt — it collapses the queue into one report while still reporting the next attempt's different fault. `web/js/runtime-bootstrap.mjs` now owns the sequence, marks the errors it raises in a `WeakSet` (not a property or a `Symbol` — the error is handed to `captureError` and serialized, and a marker must not ride along into a Sentry payload or vanish through `JSON.stringify`), publishes the handle only after seeding succeeds, and drops a rejected attempt instead of caching it, matching the reset-on-failure idiom `allDriverModulesPromise` already used. One report is also one **capture**: the crash returns through whichever action was in flight, so `reportActionError` — which FINDINGS already calls the one capture funnel — would file the same failure as a second Sentry event under a second vocabulary. The runtime therefore marks the fresh `Error` it rethrows, and the funnel logs the failed action and its status but skips the capture. It is a separate module because `runtime-rpc.js` imports Pyodide from a CDN at parse time and therefore cannot be imported by the Node suite — which is why this code had no coverage for two years of the bug's life.
- **reportActionError-is-the-one-capture-funnel** (2026-09-06): all twelve action-level failure sites in the UI already route through `reportActionError` in `web/js/ui/debug-log.js` — clone download/upload, initialization, import/export, metadata load, repeater queries — so error reporting needed exactly one insertion point rather than a `captureException` at each site. Two properties of that funnel are load-bearing and must not be "tidied up": cancellations go to `reportActionCancelled` instead, which is why a user dismissing the browser's port chooser never files a Sentry issue; and the same `classifyErrorKind`/`errorTypeName` the analytics layer uses are sent as tags, so a failure is not classified under two different vocabularies in two different consoles. Radio identity reaches the SDK through a *provider* registered once in `ui.js` (`setContextProvider`) rather than pushed on each selection, so it is read at the moment of failure and is also attached to unhandled errors that never pass through app code.
- **error-reports-are-where-user-data-leaks** (2026-09-06): the no-user-data rule is harder here than for analytics, because analytics only ever sends values this app chose while an error report sends whatever CHIRP put in the message — and "Frequency 145.500000 out of range for HOME REPEATER" is a useful bug report and a description of someone's radio at the same time. `beforeSend` therefore redacts every free-form string (frequencies in both decimal and whole-Hz form, coordinates, Maidenhead locators, quoted values, codeplug file names, URL query strings, which is where a repeater query hides a location fix), keeping the shape of the failure and dropping the values. Two exemptions are deliberate and worth preserving: exception **types** survive (`RadioError` is a CHIRP class name, and it is what makes an unrecognised failure legible), and quoted **paths** survive the quoted-value rule (`File "…/drivers/uv5r.py", line 421` is the most useful line in a Python traceback). Console breadcrumbs are dropped wholesale rather than redacted, since the debug panel's entire job is printing full tracebacks. The file-name rule is single-token on purpose: regex leftmost-matching means widening it to catch "My Radio.img" whole also eats the sentence around it, turning "could not parse backup.img" into just "[file]".
- **the-reportable-failure-happens-before-the-reporter-loads** (2026-09-06): this app's most likely failure is that the runtime never starts — Pyodide boots from jsDelivr behind a WebAssembly JSPI feature check — and that window closes before an SDK fetched from a CDN can be ready. `initSentry` therefore installs its own `error`/`unhandledrejection` listeners immediately, buffers up to ten captures, and replays them once the SDK arrives; the listeners are removed at that point, or the SDK's own global handlers would report everything twice. `version.json` is fetched concurrently with the SDK rather than before it (both are network, neither needs the other) so the release tag costs no added latency, and a missing `version.json` costs the tag rather than the report.

*Pinned by tests:*
- Off the production host the SDK is never fetched and no listeners are left behind; the host list cannot drift from `ANALYTICS_HOSTS`; the CDN URL cannot drift from the version `package.json` pins; a blocked CDN or a missing `version.json` degrades instead of throwing — `test-sentry.mjs`.
- Only a bootstrap failure counts as a runtime crash, a runtime that failed to seed is never published, and a rejected attempt is retried rather than cached; a second distinct failure is reported rather than swallowed, while callers queued behind one attempt report it once — `test-runtime-bootstrap.mjs`.
- A bootstrap failure returning through an action is captured once, and an ordinary action failure still is — `test-debug-log.mjs`.
- Every redaction rule is checked in both directions — the values that must go, and the traceback frames, exception types and version numbers that must stay — `test-sentry.mjs`.

## GitHub PR gotchas

- **pr-refs-go-stale** (2026-07-22/23): GitHub pins a PR's `base.sha` to the merge-base at creation and never advances it (phantom already-merged files stay in the diff — PR #8), and the async PR-sync job can persistently fail to advance `headRefOid` after pushes (PR #7 — recurred on every push). Same workaround for both: retarget the base and back (`gh pr edit N --base <other>` then `--base master`), which re-records both refs. `GET /repos/{owner}/{repo}/compare/master...<head>` always computes a fresh merge-base and is the reliable view of a PR's true diff. Diagnostic order: `git ls-remote` (push landed?) → compare API (GitHub sees commits?) → PR `headRefOid` (PR synced?).

- **issue-form-prefill-is-silent-when-wrong** (2026-08-16): an issue-form prefill URL (`issues/new?template=<file>.yml&<field id>=<value>`) fails quietly in both directions — a query param whose name is not a field `id` in the template YAML is dropped with no warning, and an over-long URL is answered with HTTP 414 instead of the form (there is no POST prefill to fall back on, so the URL is the whole channel). Both pre-fillers therefore measure the built URL and trim the body to fit — `web/js/ui/issue-report.js` by dropping the oldest debug lines, `web/js/loopback-issue.js` by dropping passing cases first — and `test-loopback-issue.mjs` checks every param name against the template file. A `type: textarea` with `render: text` is already fenced when rendered, so prefilling it with ``` fences double-wraps it.
