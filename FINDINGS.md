# Findings

Durable, non-obvious facts about CHIRP, the browser runtime, and the project's infrastructure.
Grouped by topic; each entry starts with a **bold slug** (grep target) and carries its discovery date.
Narrative/debugging history lives in git log — record only the rule, the mechanism, and the pointer.
Prune entries when the code or infrastructure they describe changes.

## CHIRP / Pyodide runtime

- **static-driver-catalog** (2026-06-23): `list_registered_radios()` in Pyodide imports all ~191 CHIRP drivers, each triggering a blocking jsDelivr fetch via `ChirpCdnFinder` — so the catalog is precomputed at build time (`scripts/build-catalog.mjs` → `web/radio-catalog.json`). The runtime accepts it only when its `chirpRevision` exactly matches `DEFAULT_CHIRP_REVISION` (`web/js/python-sources.mjs`), falling back to live enumeration otherwise; `build:catalog` refuses to emit on a drifted submodule. Pyodide boots lazily on first radio selection / CSV / serial action.
- **rpc-fifo-queue** (2026-06-23): the lazy import hook suspends the interpreter mid-import (JSPI `run_sync`), so two concurrent RPCs importing the same driver re-execute the module body → CHIRP raises `Duplicate radio driver id`; concurrent RPCs also clobber the shared `_sel_*` interpreter globals. All Pyodide-backed RPCs must go through the FIFO call queue (`web/js/call-queue.mjs`); only `getRuntimeInfo` bypasses it. UI-side loads carry monotonic tokens so stale responses never overwrite a newer selection.
- **gettext-builtins-come-from-wxui** (2026-07-27): CHIRP drivers call `_()` and `ngettext()` as *builtins*, but only `chirp.wxui.setup_locale()` installs them (`builtins._ = wx.GetTranslation`) — a frontend we never load. So any driver using them raises `NameError: name '_' is not defined` from otherwise-fine code paths (`uvk5.UVK5Radio.get_settings`, and its `LOG.warning` on images without a firmware trailer). `runtime_bridge.py` installs passthrough builtins before importing `chirp`; it guards on `callable()`, not `hasattr`, because a REPL binds `builtins._` to the last result. Grep hits are spread across drivers and grow with every submodule bump — treat this as runtime-wide setup, not a per-driver patch, and note `get_radio_settings()` reports the `NameError` as "backing state missing", so it only ever showed up in the debug log. `scripts/test-gettext-builtins.mjs` scans the runtime-importable CHIRP modules (top level, `drivers/`, `sources/`; not `wxui/`) for these calls and asserts each name is an installed builtin, so a bump that starts calling e.g. `pgettext()` fails loudly.
- **upstream-tests-skip-power** (2026-07-29): CHIRP has no byte-level image round-trip test at all (`grep save_mmap\|get_packed` over `chirp/tests/*.py` is empty outside the metadata unit tests). The closest is `test_brute_force.py::test_get_set_all`, which does `get_memory` → `set_memory` → `get_memory`, and `assertEqualMem` (`chirp/tests/base.py:160`) skips `power` with a bare `# FIXME`. So driver-level power round-trip defects are invisible upstream — `ftm7250d.FTM7250Radio` inverts Hi/Low on that exact sequence with no webchirp code involved. Don't expect an upstream oracle for anything power- or image-fidelity-related; also note `chirp/tests/driver_xfails.yaml` carries only `TestCaseBruteForce` entries, and `xfails.txt` is empty, so every image in `tests/images/` is expected to detect and load cleanly.
- **pyserial-shim-and-idrp-never-registers** (2026-07-30): only two drivers import pyserial at module scope (`tg_uv2p`, `idrp`); Pyodide has no `serial` module, so both raised `ModuleNotFoundError` and silently never registered (issue #29). `runtime_bridge.py` now installs a shim `serial` module (pyserial constants + a `Serial` class that refuses construction) before any driver imports; `scripts/test-pyserial-shim.mjs` pins the behavior. Note `idrp.IDRPx000V` has no `@directory.register` decorator upstream, so it does not appear in `DRV_TO_RADIO` even in desktop CHIRP — fixing its import cannot add it to the catalog, and its absence there is upstream-correct. The catalog build (`build:catalog`) now warns per unimportable module instead of dropping them silently; currently zero of 191 fail.
- **settings-need-backing-state** (2026-03-14): many drivers only materialize settings from a cached clone image, parsed file image, or live session — `get_settings()` on blank/default state can throw (missing parsed memory, `None` values; e.g. `baofeng_uv17Pro.UV17Pro`). Treat settings as unavailable until backing state exists. When instantiating for metadata enumeration, fall back to `radio_cls("")` if `radio_cls(None)` fails.
- **skip-immutable-on-apply** (2026-03-14): replaying serialized values onto a fresh settings tree includes immutable fields, which drivers reject with `This value is not mutable`; bridge-side apply logic must skip non-mutable CHIRP values entirely.
- **upstream-get-max-defect** (2026-03-14, still present 2026-07-23): vendored CHIRP's `RadioSettingValueFloat.get_max()` has no `return` (`chirp/chirp/settings.py:203`), so it returns `None`; serialize float bounds via the `_max` instance field fallback.
- **parse-freq-negative-defect** (2026-07-30): upstream `chirp_common.parse_freq()` mishandles negative decimals — it splits on `.` and sums `int(mhz) * 1e6 + int(khz)`, so the fractional part is always added: `parse_freq("-0.600000")` → **+600000** (`int("-0")` is 0) and `parse_freq("-5.600000")` → −4400000 instead of −5600000. Harmless for `to_csv`-derived rows (no driver emits negative offsets; they normalize to duplex `+`/`-`), but a hand-typed or imported negative offset is silently corrupted. The old `to_MHz(float(text))` path was sign-correct but truncates (see **row-parsing-avoids-really-from-csv**) — neither upstream parser handles both; validate/reject negative offsets before parsing if they ever need to round-trip.

## Channel grid / CSV

- **csv-parser-rejects-header-only** (2026-07-30): a CSV holding nothing but the header row is not a valid CHIRP file — `CSVRadio._load()` raises `InvalidDataError("No channels found")` when no data line yields a memory. So the editor's startup column schema cannot be obtained by round-tripping a header-only CSV through `parse_csv`; `get_default_headers()` reads `chirp_common.Memory.CSV_FORMAT` directly instead. Only the startup case needs it — a radio selection supplies `get_radio_column_metadata()` headers, which take precedence.
- **csv-export-is-import-logic** (2026-07-30): CHIRP's CSV export is not `Memory.to_csv()` on the driver's memories — it pushes each one through `import_logic.import_mem(csv_radio, rf, mem, mem_cls=chirp_common.Memory)` into a `generic_csv.CSVRadio` and saves that (`chirp/wxui/memedit.py:2758`). Three things follow that a rows→CSV writer gets wrong on its own. `CSVRadio.set_memory()` rewraps power as `AutoNamedPowerLevel(dBm_to_watts(float(level)))`, so an exported CSV always holds watts (`50W`, `5.0W`, `4.0W`) and never a driver label — and `PowerLevel.__int__` truncates the dBm, so converting with `int()` writes a 50W level as `39W`. `_import_tone`/`_import_dtcs` fill columns the source radio does not track separately (rtone→ctone, dtcs→rx_dtcs), which is why FT-60 DTCS channels export with `RxDtcsCode=263` upstream and `023` without that step. And an incompatible memory is logged and written **unconverted**, not dropped. `normalize_rows()` mirrors all of it; `scripts/test-csv-export-parity.mjs` diffs our export against a transcription of upstream's across every image in `chirp/tests/images`.
- **csv-radio-load-from-keeps-default-channel** (2026-07-30): `CSVRadio(None)` seeds a *non-empty* channel 0 at 146.010000/50W, and `CSVRadio._load()` — the path `load_from()` takes — never calls `_blank()`; only the filename path `load()` does. So every `load_from()` inherits that phantom channel: CSV imports whose channels start at location 1 gained a bogus first row, and so did exports for radios whose `memory_bounds` start at 1 (GMRS-V2, FT-60). Upstream never trips over it because `wxui/memedit.py` calls `erase_memory(0)` right after constructing its export radio. Use `_blank_csv_radio()` for any new `CSVRadio(None)`.
- **csv-parser-drops-zero-freq-rows** (2026-07-30): `CSVRadio._load()` skips any row whose frequency parses to 0 ("did not contain a valid memory"), but drivers do report non-empty memories with no frequency — uninitialised locations in `Icom_IC-W32A`, `Jetstream_JT220M` — and CHIRP exports them, because its export never round-trips through its own parser. Staging rows through a CSV document therefore *loses channels the grid shows*; `_memories_from_rows()` calls `CSVRadio._parse_csv_data_line()` per row instead, which keeps CHIRP's ATTR_MAP converters and its 50W default without the `_load()` filter. Those channels then fail `import_mem` with "Tx freq 0.000000 is out of supported range" and go out unconverted, which is also what CHIRP does.
- **dvmemory-to-csv-layout** (2026-07-30): `DVMemory.to_csv()` (`chirp/chirp_common.py:614`) still emits the pre-RxDtcsCode/CrossMode/Power layout — 18 fields where `Memory.CSV_FORMAT` has 21 — so zipping it against the headers puts the mode string in `RxDtcsCode` and shifts everything after. D-STAR images showed `RxDtcsCode=DV` in the grid and lost every DV channel on export (`[rx_dtcs] invalid literal for int(): 'DV'`; `Icom_IC-2820H` exported 12 channels in CHIRP, 0 here). CHIRP dodges it by forcing `mem_cls=chirp_common.Memory`; `_row_values_for_csv()` clones DV memories into a plain `Memory` for the same reason. Call signs are dropped either way — CHIRP's CSV export drops them too.
- **power-labels-beat-watts-in-rows** (2026-07-30): rows and the grid carry power as the driver's *label*, not watts, and that is the right way round in both directions. Of 551 driver classes, **zero** advertise two levels with the same label, but **8** collapse onto the same watt string once `dBm_to_watts()` rounds to 1 dp (`retevis_rt21.RT619Radio`/`RB628BRadio`, `radtel_t18.RB619Radio`/`RB629Radio`/`H777HPMRRadio`, `bf_t8.RetevisRB627B`, `retevis_rb28.RB628Radio` all put High and Low on `0.5W`; `radioddity_gm30.RadioddityMU5` on `2.0W`) — so watts in a cell would be ambiguous where a label is not. It also matches CHIRP, which shows watts only for `has_variable_power` radios (`ChirpVariablePowerColumn`, `chirp/wxui/memedit.py:415`, chosen at :1387) and labels for the rest: of the 452 classes advertising levels, 446 label with words and the only 6 numeric ones are CHIRP's file-format pseudo-drivers (Generic/Commander/RT Systems CSV, ARRL Travel Plus, Kenwood HMK/ITM), none of them in `web/radio-catalog.json`. The residual cost of labels: 18 driver modules define a second, *unadvertised* level list keyed by band (`vx6`/`vx7.POWER_LEVELS_220`, `ft90`'s VHF/UHF pair, …), so a label under-determines watts for channels outside the primary band and our CSV writes the advertised value (VX-6 220 MHz: `5.0W` where CHIRP writes `1.5W`). Tracked as expected divergences in `scripts/test-csv-export-parity.mjs`. Radio *writes* are unaffected — `vx6.set_memory` re-resolves power from the frequency. `_power_level_watts()` publishes the label→watt mapping so the grid can show it as a hover legend; that legend is column-level for the same band-keyed reason — `valid_power_levels` cannot say which list a given channel's level came from.
- **blank-driver-instances-misreport-features** (2026-07-30): `get_features()` on `radio_cls(None)` is not the same as on a parsed image. `retevis_rt98.Rt98Radio` advertises only the PMR level (`Low` = 0.5W) blank and the full `Low`/`Mid`/`High` set (`Low` = 5W) once an image is parsed, so a label resolved against blank features picks the wrong wattage. `_driver_features()` prefers `LAST_IMAGE_BY_DRIVER` and falls back to a blank instance; same root cause as **settings-need-backing-state**.
- **csv-power-column-ignored** (2026-03-16): `chirp_common.Memory.really_from_csv()` ignores the `Power` column entirely, leaving `mem.power` unset so `set_memory()` falls back to index 0 (`High`). Direct channel writes must set power explicitly; confirmed on real UV-5R hardware (Low uploaded, read back High). Superseded as a code path by **row-parsing-avoids-really-from-csv**, but the rule still holds for any new caller.
- **row-parsing-avoids-really-from-csv** (2026-07-29): `really_from_csv()` is a legacy parser that cannot read back what CHIRP writes — it accepts only `+`/`-`/`""` for duplex while `to_csv()` emits `split` and `off`, and it rejects tones and DTCS codes outside the standard tables. CHIRP's own `generic_csv` driver doesn't use it either (it has `_clean_duplex` handlers). `_memory_from_row_values()` in `runtime_bridge.py` parses rows directly and leaves the verdict to the driver's `set_memory()`. Two traps when touching it: resolve `Power` to the driver's **own** `PowerLevel` object (`PowerLevel.__eq__` compares dBm as a float, and `PowerLevel.__int__` truncates it — a rebuilt 50W level lands on 39W and fails `POWER_LEVELS.index()`), and parse frequencies with `parse_freq()`, since `to_MHz(float(text))` truncates 8.219000 MHz to 8218999 Hz. An unset power serializes as the string `"None"` via `"%s" % None` and must stay unset, not fall back to a default. One validation this hands away: `really_from_csv` rejected rtone/ctone outside `TONES` and dtcs codes outside `DTCS_CODES`, and many drivers encode these raw (e.g. `int(mem.ctone * 10)`) without checking — so `set_memory()` is *not* a backstop for tone values, and external CSV fed through `npm run radio:write` can plant a nonstandard tone in the image silently. The UI's enum dropdowns constrain the browser path.
- **rows-not-bytes-for-round-trip** (2026-07-29): byte-identity is a poor oracle for a load → export cycle. Of 217 upstream test images that write successfully, 170 differ in bytes while every row is identical — padding and unused regions move. Compare rows field by field (`scripts/test-channel-round-trip.mjs`); treat the 42 byte-identical images as a bonus, not a requirement.
- **paste-readonly-columns** (2026-07-23): `normalizeValue()` returns `previous` for `editable: false` columns, so pasted rows silently kept defaults (e.g. TStep reset to `2.50` on UV-5R where `has_tuning_step=False`; same for `Comment`, ctone/dtcs/offset-gated columns). Programmatic row builders (paste, repeater/GMRS imports) pass `allowReadOnly` (`web/js/ui.js`) so kind/options validation applies but the editable gate doesn't; interactive editors keep the gate.
- **grid-cost-is-option-lists** (2026-07-27): the channel grid's DOM size is dominated by `<option>` elements, not cells. Every enum cell carries the driver's full option list (rToneFreq ~50, DtcsCode ~100+), so a UV-5R row is ~380 elements, not 17 — a 503-channel codeplug is ~191,000 elements and rebuilding it took 2.0-3.7 s, which every insert/remove/move/paste paid. `web/js/ui/channel-table.js` now virtualizes the grid: only the rows overlapping `#mem-table-scroll` (plus overscan) exist, row elements are recycled by rebinding values rather than rebuilt, and cell events are delegated to the tbody. Mutations and scroll steps cost 2-4 ms at ~9,900 elements. Two consequences to keep in mind: browser find-in-page and Tab reach only the rendered rows, and anything reading the grid from the DOM must select `tr[data-row-idx]` (spacer rows stand in for the rest) instead of indexing `tbody.children`.
- **file-drop-wiring** (2026-07-27): drag-and-drop loading (`web/js/ui/codeplug-io.js`) has three non-obvious requirements. `dragover` must call `preventDefault()` or the `drop` event never fires and the browser navigates to the file instead. The drop overlay must stay `pointer-events: none`, otherwise the element that appears under the cursor becomes the drag target and cancels the drag it is announcing. And `dragenter`/`dragleave` fire once per element the pointer crosses, so overlay visibility is driven by a nesting depth counter, not by any single leave. Files are routed by extension, not MIME type: browsers report `.img` as `""` or `application/octet-stream` depending on platform, and CSV as anything from `text/csv` to `application/vnd.ms-excel`.
- **numeric-enum-matching** (2026-07-23): enum columns with numeric labels (`TStep` "5.00", `rToneFreq` "88.5", `DtcsCode` "023") must fall back to numeric-equality matching, since spreadsheets normalize values to "5", "12.5", "23".

## Radio images (.img) & metadata

- **img-detection-needs-import** (2026-07-23, fallback added 2026-07-30): `directory.get_radio_by_image()` only searches drivers already in `DRV_TO_RADIO`, and the browser imports drivers lazily — so `handleLoadImage` parses the metadata trailer first (`read_image_metadata_base64`, driver-free), resolves the module via the catalog (`findCatalogRadioForImageMetadata`: exact `rclass` class-name match, then vendor/model fallback), imports it, then runs detection. When neither the trailer nor the catalog identifies a driver (raw dump, or metadata naming a model the catalog lacks), `ensureAllDriverModules()` imports every driver so `match_model()` byte-sniffing can run — the same fallback desktop CHIRP gets for free from `import_drivers()`.
- **rclass-may-be-unregistered** (2026-07-23): image metadata `rclass` can name a directory-unregistered class — `export_image_base64` from `uv5r.BaofengUV5R` stamps that name, but the registered entry is `BaofengUV5RGeneric`. Catalog matching must keep the vendor/model fallback, and must apply `directory.MODEL_COMPAT` remaps (e.g. Retevis RT-5R → RT5R) when reading metadata.
- **live-rclass-shadows-clone-driver** (2026-07-30): a clone image's stamped `rclass` class name is not unique across modules — `Kenwood_TS-480_CloneMode.img` stamps `rclass=TS480Radio`, which exists as both `kenwood_live:TS480Radio` (live mode) and `ts480:TS480_CRadio` (clone mode), so class-first catalog matching lands on the live-mode driver and detection fails. A live radio can never own a clone image, so `handleLoadImage` treats a live-mode match (`isLiveRadio`) as unresolved and falls through to the all-drivers import, where `get_radio_by_image()` matches the metadata against the clone driver's aliases.
- **variant-ignored-in-catalog-match** (2026-07-30): `findCatalogRadioForImageMetadata` matches on `rclass` then vendor/model and **never looks at `variant`**, but CHIRP does put the distinguishing information there and the matching driver can live in a different module. `Quansheng_UV-K5_egzumer.img` stamps `vendor=Quansheng, model=UV-K5, variant=egzumer`; the matcher resolves `uvk5.OSFWUVK5Radio`, a real non-live catalog entry, so `handleLoadImage` treats the driver as resolved, skips the all-drivers sweep, and detection then raises `ImageMetadataInvalidModel: Unsupported model Quansheng UV-K5`. The right driver is `uvk5_egzumer.UVK5RadioEgzumer`, which only the sweep reaches. A resolved-but-wrong match is therefore *worse* than no match, because it suppresses the fallback — any fix has to retry through the sweep when detection fails after a fast-path resolve, not just when nothing matched.
- **image-corpus-measurements-need-fresh-runtimes** (2026-07-30): driver imports accumulate in a Pyodide session, so walking `chirp/tests/images/` in one runtime measures "a session where earlier files already imported things", not each image's own path — and the corpus is walked alphabetically, where `Alinco_DJ175.img` (no metadata trailer) triggers the full sweep on the very first file. That artifact produced both a 356/357 and a 357/357 figure for work that actually leaves one image failing. Measure per-path instead: import only what that image's branch would import (its catalog-resolved module, or the sweep), which needs no per-image runtime restart because a fast-path-only pass can only ever *hide* failures, never invent them. Current true split: 108 no-trailer + 1 live-clash sweep and load, 248 fast-path of which 247 load — see **variant-ignored-in-catalog-match** for the one that does not.
- **synchronous-python-can-drive-progress** (2026-07-30): a plain `for` loop inside one `runPythonAsync` *can* animate browser UI, which looks impossible and is why the driver sweep shipped silent at first. Every CHIRP import suspends the interpreter on a CDN fetch through `ChirpCdnFinder`'s JSPI `run_sync`, so the JS event loop runs between iterations and anything the loop wrote to the DOM paints — the same mechanism that lets CHIRP's synchronous clone loops drive `#clone-progress` via `serial_progress`. So reach for a callback argument (`import_all_driver_modules(names, progress_cb)`) before restructuring a loop into per-item RPCs; the latter would pay a full call-queue round trip per module for no benefit. Two rules for such callbacks: guard every call in `try/except` so a reporting failure can never abort the work being reported on, and clear the `pyodide.globals` slot afterwards. The reverse also holds — a Python loop that never suspends will not paint, so this is a property of the I/O, not of Pyodide.
- **all-driver-import-mechanics** (2026-07-30): `import_all_driver_modules()` (`runtime_bridge.py`) tolerates per-module failures — each failure is recorded and surfaced as `DRIVERS SKIP <module>: <error>` in the debug log, never aborting the sweep. With the pyserial shim in place (see **pyserial-shim-and-idrp-never-registers**) all 191 driver modules import and 551 radio classes register, so the skip list is empty today; keep reporting it anyway, because importability cannot be judged by grepping for `import serial` (`hf90`/`tmv71_ll` have function-scope imports that are harmless) and the next submodule bump can reintroduce a failure silently. `scripts/build-catalog.mjs` calls the same function so the catalog's "not importable, absent from catalog" warnings and the runtime's skip lines can never diverge. The sweep is one synchronous Python loop in a single `runPythonAsync` (~1.8 s in Node off the local checkout; much slower in-browser, where each module is fetched individually from jsDelivr), cached per session as a promise that resets on failure so a later load retries instead of caching the wreck.

## WebUSB serial adapters

- **ch340-version-not-bcddevice** (2026-07-28): the CH340/CH341 protocol branches on the chip version returned by vendor request `0x5F`, **not** on the USB `bcdDevice` word — an 0x1a86:0x7523 cable reporting `bcdDevice 0xc233` still reports a version of 0x30/0x31 over the wire. Version > 0x27 sets bit 7 of the prescaler value (otherwise the chip withholds data until a full 32-byte packet, which stalls short CHIRP replies); version >= 0x30 configures framing through the LCR register pair, and older parts are left at their 8N1 defaults.
- **ch340-prescaler-quirk-is-inert-here** (2026-07-28): the kernel's `CH341_QUIRK_LIMITED_PRESCALER` (detected by a failing register read on clone silicon) only changes the encoded divisor when the first-pass divisor comes out **odd**. Every baud CHIRP uses (9600/19200/38400/57600/115200) yields an even divisor, which the "prefer the lower base clock" rule already halves — so the quirk cannot regress a working cable. Pinned by a test in `scripts/test-ch340-webusb.mjs`.
- **webusb-vendor-filters-are-too-broad-for-wch** (2026-07-28): FTDI and Prolific can be filtered by vendor id alone, but WCH's 0x1a86 also covers CH9102/CH343 parts that enumerate as CDC-ACM (and non-serial chips). The CH340 chooser filters on exact vendor/product pairs so those devices fall through to the CDC polyfill instead of getting the CH340 register map.

## Hosting & deployment

- **pages-cache-window** (2026-07-22): GitHub Pages serves everything with a fixed, non-configurable `Cache-Control: max-age=600` + ETag (Fastly). This creates a ≤10-minute post-deploy window where a stale `index.html` can 404 on old content-hashed asset names. Self-healing and low-impact; if it ever matters, make `build:dist` retain the previous generation of hashed assets rather than fighting headers. Heavy payloads (Pyodide, CHIRP sources) come from jsDelivr with long cache lifetimes, not Pages.
- **pages-workflow-deploy** (2026-07-22): Pages deploys via `.github/workflows/pages.yml` from `dist/`, HTTPS enforced at `https://webchirp.jasiek.me/` (Web Serial/WebUSB require a secure context; the previous legacy Jekyll build of raw `master` had neither).
- **no-crossorigin-embeds** (2026-03-14): `buttons.github.io/buttons.js` (and similar embed widgets) cannot work under COEP/COOP cross-origin isolation, even self-hosted — hence the custom `web/js/github-button.js`.

## GitHub PR gotchas

- **pr-refs-go-stale** (2026-07-22/23): GitHub pins a PR's `base.sha` to the merge-base at creation and never advances it (phantom already-merged files stay in the diff — PR #8), and the async PR-sync job can persistently fail to advance `headRefOid` after pushes (PR #7 — recurred on every push). Same workaround for both: retarget the base and back (`gh pr edit N --base <other>` then `--base master`), which re-records both refs. `GET /repos/{owner}/{repo}/compare/master...<head>` always computes a fresh merge-base and is the reliable view of a PR's true diff. Diagnostic order: `git ls-remote` (push landed?) → compare API (GitHub sees commits?) → PR `headRefOid` (PR synced?).

## Process

- **silent-dom-guards-hid-dead-code** (2026-07-27): the `?.` / `if (!el) return` guards over `document.querySelector` results were not defensive — they concealed removals. Commit `ff5607a` deleted the `#serial-transaction` debug panel from `index.html`, but the handler in the UI survived, silently no-oping ever since (its `serialTxRx` RPC in `runtime-rpc.js` is now unreferenced). The guards also never prevented a crash: 15 of the same elements were dereferenced unguarded elsewhere, so a missing element already threw — just later and further from the cause. `web/js/ui/dom.js` now declares every element required and throws once naming all missing ones, and `scripts/test-dom-selectors.mjs` asserts each selector resolves in `index.html`. The same check caught `test-ui-radio-loading.mjs` stubbing only a subset of elements, i.e. testing a page shape production cannot have.
- **merge-can-drop-tests** (2026-07-23): the `eaeba93` upstream merge took master's `package.json` wholesale, silently dropping two clipboard test scripts from `npm run test:channels`. "Take theirs" resolutions on `package.json` need a check that branch-added test entries survive.
- **worktree-needs-submodule-init** (2026-07-27): a fresh git worktree starts with an empty `chirp/`, so `npm run test:channels` fails three Pyodide-backed tests with `Invalid CHIRP source dir` that look like real regressions. `git submodule update --init` inside the worktree fixes it and is fast — it reuses the existing `.git/modules/chirp` objects.
- **asdf-python-unset** (2026-07-23): `python`/`python3` fail in this repo ("No version is set for command python" — asdf shim, no entry in `.tool-versions`), so the documented `python -m py_compile web/python/runtime_bridge.py` validation step errors out. `/usr/bin/python3 -m py_compile ...` works as a fallback.
